# 어떻게 동작하는가

## 한 줄 요약

이 도구는 PDF를 먼저 로컬 텍스트로 바꾸고, 목차와 페이지 구조를 이용해 문서를 나눈 다음, 필요한 부분만 LLM이나 Notion으로 보냅니다.

```text
PDF
  -> pdftotext 또는 필요한 페이지만 OCR
  -> 페이지별 텍스트
  -> 목차·제목 후보 탐색
  -> 챕터 경계 확정
  -> 차례 또는 본문에서 소챕터 경계 탐색
  -> Markdown 생성
  -> 선택적으로 LLM 요약/정리
  -> 선택적으로 Notion 업로드
```

## 왜 PDF 전체를 LLM에 넣지 않는가

PDF에서 챕터를 찾는 일은 대부분 의미 이해가 아니라 구조 탐색입니다.

예를 들어 다음 정보는 로컬 도구만으로 충분합니다.

- PDF 전체 페이지 수
- `1장`, `Chapter 1`, `2.1` 같은 제목 패턴
- 목차에 표시된 페이지 번호
- 페이지별 텍스트 길이
- 같은 제목이 머리말에 반복되는지 여부

이 과정을 LLM에 맡기면 긴 PDF를 매번 전송해야 하고, 비용과 토큰 사용량이 커집니다. 반면 로컬에서 한 번 추출한 텍스트는 반복해서 사용할 수 있습니다.

## 챕터 찾기 방식

`pdf_to_chapters.py`는 다음 순서로 챕터 후보를 찾습니다.

1. `pdftotext -layout`으로 PDF를 페이지 단위 텍스트로 추출합니다.
2. `1장`, `제1장`, `Chapter 1` 같은 제목 후보를 찾습니다.
3. 제목이 페이지 상단에 있는지 확인합니다.
4. 한 페이지에 여러 챕터 번호가 나오면 목차 페이지일 가능성으로 낮게 평가합니다.
5. `무엇을 배우게 될까요?`, `Introduction` 같은 도입부 표현이 있는지 확인합니다.
6. 같은 챕터 제목이 반복되는 경우 가장 그럴듯한 첫 페이지를 선택합니다.
7. 후보별 점수와 근거를 `detection-report.json`에 저장합니다.

자동 감지가 충분하지 않은 책은 다음처럼 경계만 JSON으로 지정합니다.

```json
{
  "sections": [
    {"number": 1, "start": 23, "title": "최적 멈춤"},
    {"number": 2, "start": 63, "title": "탐색과 이용"}
  ]
}
```

이 설정은 책마다 달라지는 목차 구조만 담습니다. 텍스트 추출과 Markdown 변환 코드는 그대로 재사용됩니다.

## 소챕터 찾기 방식

`split_pdf_subsections.py`는 챕터 범위 안에서 다음과 같은 번호형 제목을 찾습니다.

```text
2.1 두 확률변수의 분포
2-2 결합확률분포의 특성치
```

같은 페이지 안에서 다음 소챕터가 시작될 수 있으므로 페이지 단위가 아니라 페이지와 줄 번호를 함께 저장합니다. 그래서 한 페이지가 두 소챕터에 걸쳐 있어도 경계를 나눌 수 있습니다.

수리 교재에서는 `2.1`이 소챕터 번호일 수도 있고 `2.1번 연습문제`일 수도 있습니다. 이 경우에는 다음과 같은 목록을 추가합니다.

```json
{
  "2": ["2.1", "2.2", "2.3", "2.4", "2.5"]
}
```

그러면 도구는 각 번호의 첫 번째 실제 제목만 소챕터로 사용하고, 뒤에 나오는 연습문제 번호는 무시합니다.

번호가 없는 책은 `pdf_toc.py`가 차례를 분석합니다.

1. `목차`라는 글자가 OCR에서 사라져도 페이지 번호가 반복되고 구분선이 있는 차례 후보를 찾습니다.
2. `|`, `｜`, OCR 결과인 `I`와 일부 깨진 구분자를 소챕터 사이의 경계로 인식합니다.
3. 각 항목 끝의 페이지 번호를 읽고, PDF 하단에 찍힌 실제 페이지 번호와 물리적인 PDF 페이지를 매칭합니다.
4. 페이지 번호가 `2.46`, `3r1`, `-:r,2`처럼 깨진 경우에는 장 범위와 앞뒤 항목의 순서를 이용해 위치를 보정합니다.
5. 결과 리포트에 `toc` 출처를 남겨 자동 감지된 경계를 확인할 수 있게 합니다.

따라서 책의 제목이나 소챕터 목록을 코드에 하드코딩하지 않습니다. 책마다 차례의 모양은 달라도, 차례의 구분자와 페이지 구조를 공통 규칙으로 처리합니다. 다만 OCR이 제목과 페이지를 모두 잃어버린 경우에는 자동 결과를 그대로 믿지 말고 `subsection-report.md`를 확인해야 합니다.

## OCR은 언제 사용하는가

처음부터 OCR을 실행하지 않습니다.

1. 먼저 내장 텍스트 레이어를 `pdftotext`로 확인합니다.
2. 텍스트가 거의 없거나 심하게 깨진 페이지만 OCR합니다.
3. OCR 결과도 다시 `detection-report`로 확인합니다.

OCR은 텍스트 추출보다 느리고 오탈자가 생길 수 있으므로 전체 PDF에 무조건 적용하지 않는 것이 효율적입니다.

한국어와 영어가 섞인 스캔 PDF는 `PaddleOCR`을 기본 엔진으로 사용합니다.
`ocr_pdf_to_markdown.py`를 실행할 때 PaddleOCR이 없으면 `.venv-paddle` 가상환경을 만들고
`paddleocr`와 `paddlepaddle`을 자동 설치합니다. 첫 실행에는 인터넷 연결이 필요합니다.

macOS에서는 대안으로 `Vision`의 `ko-KR`와 `en-US` 인식을 사용할 수 있습니다.
`ocr_pdf_to_markdown.py`가 페이지 이미지를 렌더링하고 `vision_ocr_batch.swift`를 한 번 호출해
여러 페이지를 처리한 뒤, 인식 결과를 기존 Markdown 변환기에 넘깁니다.

PaddleOCR과 Vision 모두 본문 인식에는 강하지만 수식 기호나 복잡한 표의 구조까지 보장하지 않습니다. 수식이
중요한 책은 OCR 결과를 원본 페이지와 함께 확인해야 합니다. 전체 책은 60페이지 안팎의 배치로
처리한 뒤, 이미 확인된 챕터 경계에 맞춰 Markdown을 재조립할 수 있습니다.

## Notion 업로드 방식

Notion 업로드는 변환과 분리되어 있습니다.

- Markdown 생성만 필요한 사람은 Notion 설정이 필요 없습니다.
- 업로드 전 `--dry-run`으로 페이지 수와 분할 크기를 확인합니다.
- 긴 Markdown은 여러 child page로 자동 분할됩니다.
- Notion 토큰과 부모 페이지 ID는 `.env`에만 보관합니다.

## 검증 포인트

새 PDF를 처리할 때는 다음 세 가지를 확인합니다.

1. `--dry-run` 결과의 챕터 시작 페이지가 목차와 맞는가
2. `detection-report.md`에서 마지막 챕터가 PDF 끝까지 이어지는가
3. Markdown 파일의 `원본 PDF 페이지` 범위가 서로 겹치거나 비어 있지 않은가

확신도가 낮거나 목차가 특이한 책은 자동 감지 결과를 그대로 가져가지 말고, `boundary-map.json`으로 경계를 고정한 뒤 변환합니다.
