## 변경 배경

- Phase 3A와 3B에서 `process`/`infer`/`apply`, config, inspect 명령을 공통
  result/error envelope로 전환했고, 직전 구현 `a9649efeabcf`에서 단일
  `ocr-overlay`의 진행 이벤트를 stderr의 versioned JSONL로 분리했다.
- `classify-scan`은 여전히 JSON 진행 로그와 최종 결과를 모두 stdout에 출력했다.
  이 상태에서는 agent가 stdout 전체를 단일 최종 결과로 파싱할 수 없고 명령마다
  서로 다른 출력 규칙을 알아야 했다.
- 기존 분류기는 corrupt/encrypted PDF 같은 파일별 오류를 report 행에 기록한 뒤
  나머지 파일을 계속 처리하는 내결함성 batch로 설계되어 있다. 공통 CLI 계약을
  적용하면서 이 부분 실패 의미를 훼손하지 않는 것이 필요했다.

## 결정 내용

- `classify-scan`에 canonical `--format human|json`과 `--debug`를 추가하고 공통
  `CommandResultEnvelope`/`CommandErrorEnvelope`를 사용하게 했다.
- JSON 최종 결과는 stdout 한 줄에만 출력한다. plain, Rich progress, JSONL 진행
  이벤트는 모두 stderr를 사용해 final result와 실행 중 관찰 정보를 분리했다.
- 기존 `JsonStdoutClassifyLogger`를 `JsonStderrClassifyLogger`로 교체하고 공통
  `CommandEventEnvelope` schema version 1을 사용했다. 상단에는
  `command/event/level/message`, 분류별 count와 입력 PDF는 `data`에 둔다.
- 없는 입력 디렉터리와 잘못된 log mode 등은 `invalid_input` exit 2, 명령 전체를
  중단시키는 예상하지 못한 예외는 `runtime_error` exit 1로 분류했다.
- 개별 PDF 오류로 `error_count > 0`이어도 report와 집계가 완성되면 성공 exit 0을
  유지했다. 파일별 오류는 성공 result의 `error_count`, detail JSONL/CSV, stderr
  error event로 관찰한다.

## 작동 방식

- CLI는 먼저 출력 형식과 log mode를 검증하고 입력 디렉터리 존재 여부를 확인한다.
  입력 계약 위반은 classifier나 logger를 만들기 전에 공통 error renderer로 끝난다.
- 정상 입력이면 선택한 logger와 `ClassifyBatchConfig`를 만들고 기존
  `ScanBookmarkClassifier.run()`을 호출한다. 분류 알고리즘, CSV/JSONL/summary
  artifact 형식과 파일별 오류 복구 흐름은 변경하지 않았다.
- `--log-mode json` logger는 각 `ClassifyLogEvent`를 `classify-scan` command의
  versioned event envelope로 직렬화해 stderr에 한 줄씩 기록한다. plain logger도
  stderr를 사용하며 현재 stderr 인코딩으로 표현할 수 없는 경로 문자는 대체한다.
- 실행이 끝나면 count, 실행 옵션과 report 경로를 payload로 만들고 human이면 기존
  Rich 구조화 출력, JSON이면 stdout의 result envelope 한 줄로 출력한다.
- runtime exception은 기본 모드에서 공통 error envelope로 숨기고 `--debug`에서는
  원래 예외를 다시 발생시켜 traceback을 확인하게 한다.

## 대안과 제외한 선택지

- `error_count > 0`을 `processing_failed` exit 3으로 바꾸지 않았다. 분류기는 파일별
  손상을 격리하고 부분 report를 유효한 결과로 제공하도록 처음부터 설계됐으므로,
  exit 3은 기존 batch 의미를 깨고 대규모 서재에서 정상 결과 활용을 방해한다.
- artifact인 `classification_detail.jsonl`을 새 event envelope로 바꾸지 않았다.
  터미널 event와 durable 분류 detail은 목적과 소비자가 다르며 기존 report 호환성을
  유지해야 한다.
- `ocr-overlay-batch`까지 같은 커밋에서 전환하지 않았다. OCR batch에는 batch-level
  event와 책별 `ocr-overlay` event의 command context를 분리해야 하는 추가 설계가 있어
  다음 수직 단위로 남겼다.
- Typer callback 전에 발생하는 parser-level usage error는 포함하지 않았다. 공통
  app-level Click/Typer 예외 경계가 필요한 별도 작업이다.

## 남은 리스크

- `ocr-overlay-batch`는 아직 Rich final output만 사용하고 JSON log mode의 책별 이벤트
  command가 `ocr-overlay`로 표시된다. 다음 작업에서 batch 자체 final result/error와
  event context를 함께 정리해야 한다.
- 기존 `batch` command는 config/run/item summary 계약이 없어 단순 envelope 전환보다
  Phase 7의 end-to-end batch 재구성과 함께 다루는 편이 적절하다.
- Typer parser-level 필수 인자 누락, 알 수 없는 option, option 타입 변환 오류는 여전히
  공통 JSON error envelope가 아니다.
- 분류 결과의 durable JSONL/summary는 독립적인 schema version을 아직 갖지 않는다.
