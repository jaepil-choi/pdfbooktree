## 변경 배경

- 핸드옵 문서(`docs/handoff/agent-friendly-interface-roadmap.md`) Phase 5가
  요구하는 항목 중 "두 run/plan의 added/removed/moved/level/source diff"의
  첫 수직 단위다. `inspect summary`, plan filter/limit/suspicious, metric/
  structural signal delta는 로드맵 문구만으로는 구체적인 요구가 불분명하거나
  아직 소비자가 없어 이번 범위에서 뺐다.
- 직전 커밋(`0d66ba3`, Phase 4)에서 만든 `match_bookmark_plans()`는
  "gold vs predicted" 매칭이었지만, 알고리즘 자체(title 유사도 + page
  tolerance로 1:1 매칭, matched/missed/extra 분리)는 "이전 plan vs 이후
  plan" diff와 동일한 문제다. `evaluation.py`가 Phase 4에서 미뤄뒀던
  "실제 소비자가 생기면 다시 본다"던 부분(3단계 gold quality, structural
  signal)에 대한 실제 소비자를 이번 `inspect compare`가 제공한다.

## 결정 내용

- 새 매칭 알고리즘을 만들지 않고 `match_bookmark_plans()`를 그대로
  재사용했다. `compare_bookmark_plans(before, after)`는 내부적으로
  `match_bookmark_plans(before, after, ...)`를 호출해(`before`가
  `gold` 자리, `after`가 `predicted` 자리) matched/missed/extra를 얻고,
  `missed` → `removed`, `extra` → `added`로 그대로 매핑한다. matched 쌍은
  `exact_page_match`/`level`/`source` 차이를 기준으로 `page_changed`,
  `level_changed`, `source_changed`를 후처리로 계산한다. 세 flag가 모두
  False면 `unchanged`다.
- `PlanDiffEntry`는 `status`(added/removed/matched) + `before`/`after`
  item + 세 flag를 갖는 구조로 만들었다. `moved`나 `level_changed`를
  하나의 enum 값으로 강제하지 않고 독립 boolean flag로 둔 이유는 한
  항목이 동시에 여러 변화(예: page도 바뀌고 level도 바뀜)를 가질 수
  있어서다 - 단일 `change` enum이었다면 우선순위를 임의로 정해야 했다.
- **page tolerance 기본값을 `match_bookmark_plans()`의 1이 아니라 0으로
  뒀다**(`DEFAULT_COMPARE_PAGE_TOLERANCE = 0`). gold 비교는 서로 다른
  출처(사람이 편집한 목차 vs engine 예측)라 1페이지 오차를 허용하는 게
  맞지만, "같은 pipeline의 두 실행 결과 비교"는 보통 정확히 같은 page가
  나오는 게 정상이고, page가 달라졌다면 그 자체가 `moved`로 보고할
  가치가 있는 신호이기 때문이다. CLI에서 `--page-tolerance`로 덮어쓸 수
  있게 열어뒀다.
- gold 로딩 wrapper를 안 만든 것과 같은 이유로, plan 파일을 읽는 wrapper도
  `evaluation.py`에 넣지 않았다. `inspection.py`의 `inspect_compare_plans()`
  가 기존 `load_bookmark_plan_json()`(이미 `apply` CLI가 쓰는 검증된
  loader)으로 두 plan 파일을 읽어 `compare_bookmark_plans()`에 넘기고,
  결과를 JSON 친화적 `dict`로 변환하는 presentation 계층 역할만 한다.
  이 저장소의 기존 관례(`evaluation.py` = 알고리즘/dataclass,
  `inspection.py` = 읽기 전용 dict 응답)를 그대로 따른 것이다.
- CLI `inspect compare <plan_a> <plan_b>`는 기존 `inspect plan`/
  `inspect bookmarks` 등과 완전히 같은 계약(`--format human|json`,
  `--json` 호환 alias, `--debug`, exit 2/1 정규화)을 그대로 재사용했다.
  `PlanError`(`ValueError` 하위 클래스)가 이미 `(FileNotFoundError,
  ValueError)` catch에 걸리므로 새 예외 처리를 추가하지 않았다.

## 작동 방식

- `inspect_compare_plans(plan_a, plan_b, *, page_tolerance=None,
  title_similarity_threshold=None)`는 먼저 `_require_file()`로 두 경로의
  존재를 확인해 일관된 `FileNotFoundError`를 내고, `load_bookmark_plan_json()`
  으로 각각을 `list[BookmarkPlanItem]`으로 읽는다. `page_tolerance`/
  `title_similarity_threshold`가 `None`이면 `compare_bookmark_plans()`의
  기본값(0, 0.7)을 그대로 쓴다.
- 반환 dict는 `plan_a_path`/`plan_b_path`/item count, 6가지 집계 count
  (added/removed/matched/unchanged/moved/level_changed/source_changed),
  그리고 `entries` 목록(각 entry는 `status`, `title_similarity`, 세 flag,
  `before`/`after`의 title/level/pdf_page/source)으로 구성된다.
- CLI는 `--page-tolerance`(기본 0), `--title-similarity-threshold`(기본
  0.7)를 노출해 호출자가 두 plan의 "같은 항목" 판정 기준을 조정할 수
  있게 한다.

## 대안과 제외한 선택지

- `PlanDiffEntry.status`를 `unchanged`/`moved`/`level_changed`/
  `source_changed`/`added`/`removed`처럼 세분화된 단일 enum으로 만드는
  방안을 검토했지만, 한 항목이 `moved`이면서 동시에 `level_changed`일 수
  있어 우선순위를 임의로 정해야 하는 문제가 있었다. `status`는
  added/removed/matched 세 가지로만 굵게 나누고, matched 안에서 무엇이
  바뀌었는지는 독립 boolean flag로 표현하는 편이 정보 손실이 없었다.
- `evaluation.py`에 gold/plan 파일을 읽는 wrapper(`load_plan_for_compare()`
  같은)를 추가하는 방안도 검토했지만, `inspection.py`가 이미 그 계층
  (I/O + dict 변환)을 담당하고 있어 새 계층을 추가할 이유가 없었다.
- 두 output_dir을 받아 `bookmark_plan.json`을 자동으로 찾는 편의 기능
  (`inspect plan`처럼)은 이번 범위에서 뺐다. plan 파일 경로 두 개를
  직접 받는 인터페이스가 더 명시적이고, 필요해지면 다음 증분에서 얇게
  추가할 수 있다.

## 남은 리스크

- `compare_bookmark_plans()`가 내부적으로 재사용하는
  `match_bookmark_plans()`의 그리디 1:1 매칭은 동점 점수에서 `set` 순회
  순서에 의존하는 특성이 있다(구현 노트 056에서 이미 기록한 리스크).
  두 plan 비교에서도 동일하게 적용된다.
- `inspect summary`, plan item filter/limit/suspicious item, metric/
  structural signal delta는 여전히 미착수다. `inspect compare`가 실제로
  쓰이면서 필요가 확인되면 다음 증분에서 다룬다.
- CLI가 plan 파일 경로만 받고 output_dir 자동 탐색을 지원하지 않아,
  agent가 `infer` run의 output_dir을 알아도 `bookmark_plan.json`
  파일명을 직접 붙여야 한다.
