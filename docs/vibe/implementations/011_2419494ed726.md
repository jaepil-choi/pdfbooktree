## 변경 배경

- 300STUDY의 bookmark 보유 PDF만 대상으로 TOC start page pseudo label 산출물을 만들 필요가 있었다.
- 초기 구현은 `src/pdfbooktree/toc/` 아래에 pseudo label workflow를 두는 방향이었지만, 이 작업은 패키지의 핵심 TOC 알고리즘이라기보다 데이터 제작 job에 가깝다.
- `detect_from_bookmarks.py`는 `pages + bookmarks -> TocDetectionResult`를 계산하는 핵심 알고리즘으로 유지하고, pseudo label 산출물 생성은 project root의 `outputs/`에 쓰는 스크립트 작업으로 분리하는 편이 책임 경계가 명확하다.

## 결정 내용

- TOC start page pseudo label 생성 기능을 패키지 public interface로 만들지 않고 `scripts/make-toc-start-pseudo-labels.py`에 둔다.
- 생성된 pseudo label은 수동 검수 전 ground truth가 아니므로 각 row에 `label_source=bookmark_guided_toc_start_pseudo_label`, `review_status=unreviewed`를 기록한다.
- 산출물 기본 위치는 `outputs/300study_toc_start_pseudo_labels.json`과 `outputs/300study_toc_start_pseudo_labels.csv`로 잡고, `.gitignore`에 `outputs/`를 추가했다.
- confidence 상/하위 검토 큐는 별도 `scripts/summarize-toc-start-pseudo-labels.py`에서 읽도록 분리했다.
- 스크립트 회귀 테스트는 `tests/test_toc_start_pseudo_labels.py`에서 임시 PDF와 bookmark를 만들어 검증한다.

## 작동 방식

- `make-toc-start-pseudo-labels.py`는 입력 디렉터리에서 PDF를 찾고, bookmark가 없는 PDF는 `skipped_no_bookmark_count`로만 집계한다.
- bookmark가 있는 PDF는 앞부분 text를 추출하고 `detect_toc_pages_from_bookmarks()`를 호출해 TOC range 후보를 만든다.
- detection 결과의 `start_page`, `end_page`, `pages`, candidate evidence를 pseudo label row로 변환한다.
- page number는 기존 패키지 규칙과 같이 1-based PDF page number를 그대로 사용한다.
- worker가 2 이상이면 PDF 단위로 `ProcessPoolExecutor`를 사용한다.
- JSON에는 batch summary와 labels 배열을 함께 저장하고, CSV에는 검수용 row를 평평하게 저장한다.

## 대안과 제외한 선택지

- `src/pdfbooktree/toc/start_pseudo_labels.py`에 workflow를 두는 접근은 제외했다. pseudo label 생성은 제품 기능보다는 데이터 산출 작업이고, `toc` 패키지는 핵심 detector와 parser 중심으로 유지하는 편이 낫다.
- `pdfbooktree make-toc-start-pseudo-labels` CLI 명령으로 노출하는 접근도 제외했다. 현재 작업은 300STUDY 산출물 생성 job이며, 패키지 CLI의 장기 public contract로 고정하기에는 이르다.
- 공통 runner를 새로 두는 접근도 제외했다. `bookmark_batch.py`와 pseudo label script의 중복은 일부 있지만, 지금 단계에서는 추상화보다 script/job 경계를 명확히 하는 것이 더 중요하다.

## 남은 리스크

- pseudo label confidence는 heuristic evidence를 조합한 검수 우선순위용 점수이며, 실제 TOC start page 정답 확률로 해석하면 안 된다.
- bookmark-guided TOC range는 300STUDY 검수에서 부정확한 사례가 확인되었으므로, 생성된 row는 수동 검수 전 학습 정답으로 사용하지 않는다.
- 실제 300STUDY 전체 실행 산출물은 `outputs/`에 남지만 Git에는 포함하지 않는다.
