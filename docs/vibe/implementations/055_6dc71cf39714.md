## 변경 배경

- Phase 3A~3C에서 `process`/`infer`/`apply`, `config`/`inspect`, 단일
  `ocr-overlay`, `classify-scan`에 공통 result/error/event 계약을 순서대로
  적용했다. 마지막으로 남은 것이 `ocr-overlay-batch`였다.
- `ocr-overlay-batch`는 여전히 `rich_print(to_jsonable(...))`로 최종 결과를
  stdout에 찍기만 했고, `--format`/`--debug`가 없었으며, 입력 디렉터리
  존재 검증도 없었다. agent가 다른 command와 동일한 방식으로 최종 결과를
  파싱할 수 없었다.
- 더 근본적인 문제는 `JsonStderrOcrLogger`가 `command="ocr-overlay"`를
  하드코딩하고 있었다는 점이다. `ocr-overlay-batch`가 내부적으로
  단일 OCR과 같은 logger 조립 경로(`build_ocr_logger` /
  `FlatBatchOcrProgress`)를 공유하기 때문에, batch 실행 중 책마다 나가는
  JSON event도 전부 `command: "ocr-overlay"`로 찍혀 agent가 단일 실행과
  batch 실행을 이벤트만으로 구분할 수 없었다.

## 결정 내용

- `command`를 logger 조립 체인 전체에 keyword-only 파라미터로 흘려보내는
  방식을 택했다. `JsonStderrOcrLogger`는 이미 `command` 생성자 인자를
  받고 있었으므로, `build_ocr_logger(..., command="ocr-overlay")`와
  `build_batch_ocr_progress(..., command="ocr-overlay-batch")`,
  `FlatBatchOcrProgress(mode, command=...)`,
  `OcrOverlayBatchRunner(config, ..., command="ocr-overlay-batch")`에 각각
  기본값이 있는 `command` 파라미터를 추가해 단일 command는 여전히 기본값만
  으로 동작하고 batch만 다른 기본값을 명시적으로 갖게 했다.
- `ocr_overlay_batch_cmd`는 기존 `process`/`ocr-overlay`/`classify-scan`과
  동일한 패턴을 그대로 재사용했다: `_stage_output_format` → log-mode 검증
  → 입력 디렉터리 존재 검증 → `try/except`로 `OcrOverlayBatchConfig`
  생성과 `runner.run()`을 감싸고 `(FileExistsError, FileNotFoundError,
  NotADirectoryError, ValueError, typer.BadParameter)`는 exit 2,
  나머지 `Exception`은 `_exit_stage_runtime_error`(exit 1, `--debug`시
  원래 traceback)로 처리 → 성공 시 `emit_command_result()`.
- `failed_count > 0`인 부분 실패는 command 전체 실패로 취급하지 않기로
  했다. `OcrOverlayBatchRunner._process_one()`은 이미 책 하나의 실패를
  `OcrOverlayBatchFileResult(status="failed", error=...)`로 report에
  격리하고 다음 책을 계속 처리하는 구조였다. 이 의미를 그대로 존중해
  `classify-scan`의 `error_count`와 동일하게 exit 0 + `failed_count`를
  유지하고, `exit_command_error`를 부분 실패에 호출하지 않았다. command가
  중간에 죽는 경우(예: report 파일을 쓸 수 없는 경우)만 runtime error로
  exit 1이 된다.
- 파일용 `ocr_log.jsonl`/`ocr_progress.json`과 batch report artifact
  (`ocr_overlay_batch_report.csv`, `_detail.jsonl`, `_summary.json`)
  형식은 바꾸지 않았다. terminal JSONL event만 versioned envelope로 감쌌다.

## 작동 방식

- `ocr_overlay_batch_cmd`는 `command = "ocr-overlay-batch"`를 고정값으로
  두고, 나머지는 다른 단계형 command와 동일한 helper
  (`_stage_output_format`, `_exit_stage_input_error`,
  `_exit_stage_runtime_error`, `emit_command_result`)를 그대로 쓴다.
  `OcrOverlayBatchRunner`를 생성할 때 `command` kwarg를 명시적으로 넘기지
  않는다 — 기본값이 이미 `"ocr-overlay-batch"`이기 때문이다(단일
  `ocr-overlay`가 `build_ocr_logger`를 command 인자 없이 호출해 기본값
  `"ocr-overlay"`를 그대로 쓰는 것과 대칭이다).
- `OcrOverlayBatchRunner.run()`은 `build_batch_ocr_progress(self.log_mode,
  total_pages, total_books, command=self.command)`를 호출해 progress
  조립기에 command를 전달한다. `log_mode="json"`일 때만 실제로
  `FlatBatchOcrProgress`가 만들어지고, 그 안의 `logger_for_book()`이
  `build_ocr_logger(self._mode, Path(name), enable_file=False,
  command=self._command)`로 책마다 `JsonStderrOcrLogger(command=
  "ocr-overlay-batch")`를 만든다. `tqdm`/`plain`/`none` 모드는 JSON event를
  만들지 않으므로 command 값이 출력에 영향을 주지 않는다.
- 성공 payload는 기존 필드(`total_pdf_count`, `target_count`,
  `processed_count`, `dry_run_count`, `skipped_count`, `failed_count`,
  `elapsed_sec`, `report_csv_path`, `detail_jsonl_path`, `summary_path`)를
  그대로 유지해 CSV/JSONL/summary 소비자와의 호환성을 지켰다.

## 대안과 제외한 선택지

- `command`를 `OcrLogger`/`BatchOcrProgress` protocol의 필수 인자로
  바꾸는 방안은 제외했다. 기존 `NullOcrLogger`, `PlainTextOcrLogger`,
  `TqdmOcrLogger` 등 command와 무관한 logger까지 모두 고쳐야 해서 변경
  범위가 이번 작업 목적(JSON event의 command 표시)보다 커진다.
- `ocr-overlay-batch`의 부분 실패(`failed_count > 0`)를 `process`/
  `infer`/`apply`처럼 exit 3(`processing_failed`)으로 처리하는 방안도
  검토했다. 하지만 `process` 계열의 exit 3은 "pipeline이 예외 없이
  끝났지만 단일 유효 결과를 만들지 못한 경우"를 뜻하는 반면, batch는
  여러 책 중 일부가 실패해도 완성된 report를 만드는 구조라
  `classify-scan`과 같은 부분 실패 의미(exit 0 + count)가 더 맞는다고
  판단했다.
- 기존 `batch`(bookmark 처리용) command까지 이번에 같이 전환하는 방안은
  범위를 넘어서므로 제외했다. handoff 문서(§8, §12)가 이미 Phase 7로
  분리해 두었다.

## 남은 리스크

- Typer가 command 함수 호출 전에 처리하는 필수 옵션 누락이나 타입 변환
  오류는 여전히 공통 JSON error envelope 대상이 아니다. `ocr-overlay`,
  `classify-scan`과 동일한 기존 제약이다.
- 기존 `batch`(bookmark 처리) command는 아직 이 계약을 쓰지 않는다.
  Phase 7에서 config/run/item summary와 함께 다룰 예정이다.
- `OcrOverlayBatchRunner`가 top-level에서 예외를 던지는 경로(report
  파일 쓰기 실패 등)는 테스트에서 직접 재현하지 않고 `FailingRunner`로
  runner 자체가 예외를 던지는 경계만 검증했다. 실제 I/O 실패 시나리오는
  낮은 confidence로 남아 있다.
