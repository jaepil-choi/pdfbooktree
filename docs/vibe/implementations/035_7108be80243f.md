## 변경 배경

- 300STUDY 전체에서 OCR overwrite 대상 PDF를 고른 뒤, 사용자는 CSV를 PowerShell loop로 돌리는 우회가 아니라 폴더 단위 recursive batch command를 요구했다.
- 직전 classify-scan 결과는 target PDF 목록을 만들 수 있었지만, 실제 OCR overlay는 단일 PDF CLI만 있어서 1000개 이상 서재를 운영하기 어려웠다.
- `--dry-run`은 후속 변경 작업을 하지 않는다는 의미이고, report 저장 여부는 별도 선택이어야 한다는 피드백도 있었다. 따라서 classify 단계의 dry-run과 report 기록 계약을 분리할 필요가 있었다.
- 300STUDY dry-run 관찰 결과 strict `scanned_page_fraction == 1.0`은 일부 거의 전부 scan-like인 책을 놓칠 수 있어 문서 단위 scanned threshold를 0.9로 완화하고, sampling page 수도 20에서 50으로 늘렸다.

## 결정 내용

- 새 public interface로 `OcrOverlayBatchConfig`, `OcrOverlayBatchRunner`, `OcrOverlayBatchResult`, `OcrOverlayBatchFileResult`를 `pdfbooktree.ocr.batch`에 추가하고 `pdfbooktree.ocr`에서 export했다.
- CLI에는 `pdfbooktree ocr-overlay-batch <input_dir>`를 추가했다. `--recursive`, `--dry-run`, `--force`, `--confirm-bookmark-ocr-overwrite`, `--engine-option`, `--log-mode` 등 단일 OCR overlay와 유사한 옵션을 제공한다.
- batch output은 원본 PDF를 직접 덮어쓰지 않고 `output_dir/pdfs/<relative_path>.pdf`에 저장한다. 파일별 cache, stats, log는 `output_dir/artifacts/<relative_path without .pdf>/` 아래에 둔다.
- batch report는 `ocr_overlay_batch_report.csv`, `ocr_overlay_batch_detail.jsonl`, `ocr_overlay_batch_summary.json`으로 저장한다. 파일별 row는 즉시 flush해 장시간 실행 중에도 중간 결과를 보존한다.
- `ClassifyBatchConfig`에는 `write_report`를 추가했다. `dry_run`은 변경 작업 방지 의미로 남기고, report 파일 기록은 `--write-report/--no-write-report`가 결정한다.
- 문서 단위 scanned 판정은 `scanned_page_fraction >= 0.9`와 `total_visible_chars_sampled == 0`을 함께 만족해야 true가 되도록 바꿨다. `DEFAULT_MAX_SAMPLE_PAGES`는 50으로 올리고 CLI 기본값도 같은 상수를 사용하게 했다.
- Windows 콘솔이 cp949로 표현할 수 없는 파일명을 출력하다 batch가 중단되지 않도록 classify plain/json stdout logger는 현재 stdout encoding에서 표현 불가한 문자를 replacement로 치환해 출력한다.

## 작동 방식

- `OcrOverlayBatchRunner.run()`은 input directory에서 PDF 목록을 찾고 각 파일을 `_process_one()`으로 순차 처리한다. recursive 옵션이 켜지면 `**/*.pdf`를 사용한다.
- 각 PDF는 먼저 `classify_scan(max_sample_pages=50)`과 `extract_existing_bookmarks()`/`has_meaningful_bookmark()`로 target 여부를 다시 판정한다. target은 scanned이고 meaningful bookmark가 없는 PDF다.
- target이 아니면 status=`skipped`로 report에 남긴다. `--dry-run`이면 target PDF도 OCR API 호출 없이 status=`dry_run`으로 남긴다.
- 실제 처리에서는 target PDF마다 `OcrOverlayConfig`를 만들고 기존 `OcrOverlayBuilder`를 호출한다. 기존 output PDF가 있고 `--force`가 없으면 status=`skipped`, reason=`output_exists`로 남긴다.
- 파일별 OCR 실패는 batch 전체를 중단하지 않고 status=`failed`, error 문자열로 남긴다. batch summary는 target, processed, dry_run, skipped, failed count를 집계한다.
- CLI command 한 줄 예시는 다음과 같다.
  `uv run pdfbooktree ocr-overlay-batch data/300STUDY --output-dir outputs/300STUDY --recursive --confirm-bookmark-ocr-overwrite --engine upstage --render-dpi 300 --max-sample-pages 50 --engine-option max_retries=3 --engine-option retry_initial_wait_sec=2 --log-mode plain`

## 대안과 제외한 선택지

- CSV를 PowerShell loop로 읽어 단일 `ocr-overlay`를 반복 호출하는 방식은 제외했다. 임시 실행은 가능하지만 제품 CLI가 target 판정, output path 규칙, resume/skip, 파일별 실패 기록을 책임지는 편이 300STUDY 같은 대량 작업에 맞다.
- 기존 `classify-scan` CSV를 batch 입력으로 삼는 전용 command는 이번 단계에서 제외했다. classification 기준이 코드 안에 있으므로 batch runner가 입력 폴더에서 target을 다시 판정하면 별도 CSV 동기화 문제가 없다.
- 원본 PDF 경로에 in-place overwrite하는 방식은 제외했다. OCR text object 제거와 새 invisible layer 삽입은 되돌리기 어려우므로 output root 아래에 같은 상대경로 구조로 새 PDF를 만드는 정책을 유지했다.
- `dry_run=True`일 때 report를 항상 막는 기존 계약은 제외했다. 사용자가 검토할 CSV가 필요하므로 변경 작업 여부와 report 저장 여부를 별도 flag로 분리했다.

## 남은 리스크

- `ocr-overlay-batch`는 현재 순차 실행이다. Upstage API 비용과 rate limit을 고려하면 안전하지만, 많은 책을 처리하면 오래 걸린다. 병렬 실행은 cache와 rate limit 정책을 정한 뒤 별도 구현해야 한다.
- batch runner는 target 판정을 다시 수행하므로 이미 생성한 classify CSV와 target 개수가 다를 수 있다. threshold나 sampling 설정을 CLI에서 명시해 같은 기준을 유지해야 한다.
- 파일별 OCR 로그는 각 artifact directory 아래에 흩어진다. 대량 작업 중 전체 진행률을 하나의 progress 파일로 모으는 상위 batch logger는 아직 없다.
- 기존 output이 있을 때 기본 skip 정책은 재시작에 유리하지만, 실패한 partial artifact directory 정리까지 자동으로 하지는 않는다.
