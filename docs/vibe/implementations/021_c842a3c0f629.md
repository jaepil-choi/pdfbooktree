## 변경 배경

- 구현 노트 020(`ec42888d60fa`)에서 `estimate_page_offset`를 라이브러리로 이식하고 테스트까지 마쳤지만, runtime `Processor`는 이 함수를 호출하지 않아 파이프라인이 끊겨 있었다. `Processor.run`은 `offset=None`을 하드코딩하고 "offset 추정 미지원" 경고와 함께 항상 `failed`로 끝났다.
- offset을 소비하는 `align_toc_items`(`alignment/match.py`), `calculate_content_ranges`(`alignment/ranges.py`), `extract_heading_candidates`(`alignment/headings.py`)는 이미 구현되어 있었으나 누구도 호출하지 않는 dangling 함수였다. 즉 building block은 전부 존재하고 오케스트레이션만 없는 상태였다.
- 사용자가 범위를 wire_only로 한정했다: offset → alignment → ranges 연결까지만 하고, 출력 writer(`write_bookmarked_pdf`, `export_markdown_tree`)는 stub으로 둔다.
- offset fast-fail 정책도 사용자가 명시했다: 단일 처리에서는 `OffsetEstimationError`를 그대로 전파해 중단하고 `status="failed"`로 뭉개지 않는다. 다만 batch 전체가 한 PDF 때문에 멈추면 안 되며, 그 PDF만 failed로 기록하고 로그를 남긴 뒤 다음으로 진행해야 한다.

## 결정 내용

- `ProcessingConfig`에 `offset: OffsetEstimationConfig` 필드를 추가하고, default_factory 참조가 클래스 정의 시점에 해석되도록 `OffsetEstimationConfig`를 `ProcessingConfig`보다 위로 옮겼다.
- `Processor.run`은 `parse_toc_items` 직후 `estimate_page_offset(self.input_pdf, self.config.offset)`를 호출한다. 예외를 잡지 않아 clean하지 않으면 `OffsetEstimationError`가 그대로 호출자에게 전파된다(fallback 없음). 향후 `ignore-offset-error` 옵션을 붙일 수 있도록 호출 지점을 단순하게 유지했다.
- heading 후보는 item별 예상 PDF page(`printed_page + offset`) 주변 window page text가 필요하다. `extract_page_texts`는 앞 `max_toc_search_pages`(기본 80)만 읽으므로 본문 깊은 page를 못 본다. 그래서 모든 item의 window page를 한 set으로 모아 `[1, total_pages]`로 clamp한 뒤 `extract_selected_page_texts`로 **한 번만** 추출한다(item마다 PDF 재오픈 방지).
- intermediate는 신규 이름을 만들지 않고 `INTERMEDIATE_FILENAMES`에 이미 등록된 키(`page_offset`, `toc_aligned`, `ranges`)를 그대로 사용했다.
- `ConfidenceSummary.offset`는 offset modal_share, `alignment`는 aligned item confidence 평균(없으면 0.0)으로 채운다.
- `status`는 출력 writer가 stub이라 `"failed"`를 유지하되, 경고에서 offset/alignment 문구를 빼고 남은 stub("PDF bookmark 삽입과 Markdown export")만 언급하도록 정리했다.
- batch 회복력은 `Processor`가 아니라 `BatchProcessor` 계층에 두었다. `BatchProcessor.run`이 각 PDF를 `_run_one`으로 감싸 `OffsetEstimationError`를 catch하고, `logging.warning`으로 로그를 남긴 뒤 `_record_offset_failure`로 `status="failed"` 결과와 report를 만들어 다음 PDF로 진행한다. 단일 `Processor`의 fast-fail 계약은 그대로 두고 batch 레이어에서만 degrade한다.

## 작동 방식

- 흐름: `extract_existing_bookmarks`(bookmark 있으면 skip) → `extract_page_texts`(앞 80p) → `calculate_page_features` → `detect_toc_pages` → `parse_toc_items` → `estimate_page_offset` → item별 window text 추출 → `extract_heading_candidates` → `align_toc_items` → `calculate_content_ranges` → intermediate 저장 + `ConfidenceSummary` 채움.
- 모든 page 번호는 1-based다. `_build_heading_candidates`는 `printed_page`가 없는 item은 건너뛰고, window page를 `[1, total_pages]`로 clamp하므로 offset이 음수거나 추정 page가 문서 범위를 벗어나도 `extract_selected_page_texts`의 범위 예외를 피한다.
- heading 후보가 없으면 `align_toc_items`가 offset만으로 page를 채우고(`method="offset_only_scaffold"`), 후보가 매칭되면 `offset_plus_heading_match_scaffold`로 표시한다.
- 단일 처리: offset이 clean하지 않으면 `Processor.run`이 예외로 중단된다. CLI 단일 경로(`cli.py`)도 동일하게 전파된다.
- batch 처리: `BatchProcessor`가 PDF별로 격리해 offset 실패를 failed 결과로 흡수하고 batch는 끝까지 돈다. 실패 PDF에도 report JSON이 남는다.

## 대안과 제외한 선택지

- offset fast-fail을 `Processor`가 잡아 `offset=None`으로 graceful degrade하는 안은 제외했다. 사용자가 단일 처리는 fail-fast가 기본이라고 명시했고, degrade는 나중에 `ignore-offset-error` 옵션으로 분리하기로 했다.
- batch 회복력을 `Processor` 내부에서 처리하는 안도 제외했다. 그러면 단일 fast-fail 계약이 깨진다. 책임을 batch 레이어로 올려 단일/배치 정책을 분리했다.
- heading alignment를 위해 본문 전체 text를 추출하는 안은 비용 때문에 제외하고, item window page만 선택 추출했다.
- intermediate에 새 파일 이름을 추가하는 안 대신 기존 등록 키를 재사용해 출력 계약을 단순하게 유지했다.

## 남은 리스크

- `status`는 wire_only 범위라 항상 `failed`다. offset·탐지·alignment가 모두 성공해도 출력 writer가 stub이라 `processed`가 될 수 없다. bookmark 삽입/markdown export 구현 시 status 분기를 다시 설계해야 한다.
- runtime TOC item 파싱은 결정적 regex(`toc/parse.py`)만 쓴다. 한국어/스캔 OCR 목차(예: `알고리즘_인생을계산하다`)는 영어/숫자 패턴에 안 맞아 item이 0개가 된다. experiment 014에서 검증된 `LlmTocExtractor`는 아직 `Processor`에 연결돼 있지 않다.
- offset fast-fail된 PDF는 현재 그냥 거부된다. 향후 사용자가 `--offset`으로 수동 지정하는 경로를 추가할 예정이다.
- heading alignment는 여전히 scaffold 품질(fuzzy 임계값 70, 상단 8줄 휴리스틱)이라 matched page 정확도 측정/튜닝이 후속 과제다.
- 장별 page 번호 리셋(multi-segment numbering) 책은 단일 global offset이 안 맞을 수 있다. 현재 샘플에는 사례가 없었다.
