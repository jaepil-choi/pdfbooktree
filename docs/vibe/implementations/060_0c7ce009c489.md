- Phase 7 2차 증분에서 각 PDF의 immutable item run manifest는 만들었지만,

## 결정 내용

- 단일 PDF의 `run.py`와 책임을 섞지 않고 `batch_run.py`를 신설했다. schema version
  1의 `BatchRunManifest`와 `BatchRunContext`가 batch 단위
  `created -> running -> succeeded/failed` lifecycle을 관리한다.
- batch run directory는 기존 item run과 충돌하지 않도록
  `output_root/_batch_runs/<batch_run_id>`에 만든다. resolved config와
  `batch_manifest.json`을 이 immutable directory에 함께 저장한다.
- `batch_run_id`는 실행 시각, 입력 선택 hash, config hash를 조합한다. 입력 선택
  hash에는 resolved input directory, recursive 여부와 발견된 PDF 경로 목록을 넣는다.
- 개별 item 실패는 기존 계약대로 command 실패가 아니다. `failed_count > 0`이어도
  batch manifest는 `succeeded`이고, logger나 batch infrastructure 예외처럼 command
  자체가 중단된 경우에만 `failed`와 error type/message를 기록한다.
- `BatchResult`에 `batch_run_id`, `batch_run_dir`, `batch_manifest_path`,
  `config_hash`를 추가해 Python API와 CLI JSON result가 durable manifest를 직접
  가리키게 했다.
- batch manifest의 item reference는 `run_id`, `manifest_path`, status와 실제로
  존재하는 output 경로만 기록한다. 상세 artifact/report/config는 item manifest를
  canonical source로 유지해 중복을 피했다.

## 작동 방식

- `BatchProcessor.run()`은 PDF 목록을 먼저 고정한 뒤 batch context를 만들고 running
  상태를 기록한다. 이후 기존 `_run_one()`으로 item별 run을 실행한다.
- 정상적으로 모든 item 순회와 logger 종료가 끝나면 `BatchResult`를 만들고,
  `BatchRunContext.complete()`가 집계와 item run reference를 manifest에 연결한다.
- item 처리 예외는 `_run_one()`에서 failed item으로 격리되므로 전체 batch는 계속된다.
  반대로 event logger, batch manifest 갱신 전 단계 등 바깥 예외는 partial result를
  조립해 `BatchRunContext.fail()`에 넘긴 뒤 원래 예외를 다시 발생시킨다.
- `BatchRunSummary.completed_count`를 별도로 둬 command 중단 시 발견한 전체 PDF 수와
  실제로 완료한 item 수를 구분한다.
- logger close가 실패한 경우에도 failed batch manifest를 남기도록 정상 경로에서
  close를 manifest complete보다 먼저 실행한다. 실패 경로의 재차 close 오류는 원래
  command 오류를 가리지 않도록 log만 남긴다.

## 대안과 제외한 선택지

- batch summary를 CLI JSON에만 유지하는 방식은 장시간 실행 후 터미널 출력을
  잃으면 감사와 재현이 불가능해 제외했다.
- `RunManifest`를 input directory에도 재사용하는 방식은 단일 PDF hash/page count라는
  모델과 맞지 않아 제외했다. lifecycle 패턴과 `ToolIdentity`만 재사용하고 batch
  manifest schema를 분리했다.
- item의 artifact와 report 전체를 batch manifest에 복제하는 방식은 두 manifest가
  서로 달라질 수 있어 제외했다. batch는 item manifest와 실제 output만 연결한다.
- 입력 PDF 전체 content hash를 batch 생성 시 미리 다시 계산하는 방식은 item run이
  이미 각 파일 hash를 기록하고 대량 batch 시작 비용을 늘리므로 제외했다.

## 남은 리스크

- selection hash는 발견된 경로 목록을 고정하지만 파일 content 자체는 포함하지 않는다.
  실제 content identity는 각 item manifest의 SHA-256을 따라가야 한다.
- 입력 PDF가 매우 많으면 `discovered_pdf_paths`와 `item_runs` 때문에 manifest가 커질
  수 있다. 현재 1천여 권 규모에서는 단일 JSON으로 충분하다고 판단했다.
- batch run directory를 만들거나 최초 manifest 자체를 쓰지 못하는 infrastructure
  실패는 durable identity가 생기기 전이므로 failed manifest를 남길 수 없다.
- cache/resume와 batch manifest 기반 재개는 아직 없으며 Phase 6 범위다.
- `ocr_policy` public contract 정리와 README/artifact/exit-code 문서화는 Phase 7의
  다음 작업으로 남아 있다.
