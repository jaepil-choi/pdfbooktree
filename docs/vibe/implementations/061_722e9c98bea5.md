## 변경 배경

- `data/300STUDY`처럼 규모가 큰 PDF 디렉터리에서 OCR 비용과 실행 시간을 통제하려면 page 수를 기준으로 batch 대상을 제한할 수 있어야 했다.
- 기존 `ocr-overlay-batch`는 scan 여부와 meaningful bookmark 유무만 판정했기 때문에, "100쪽을 초과하는 책" 같은 조건은 외부 staging script 없이는 public interface로 표현할 수 없었다.

## 결정 내용

- CLI에 `--min-page-count`를 추가하고, 지정값 이상의 PDF만 OCR target이 되도록 inclusive 기준을 사용했다. 따라서 100쪽 초과 조건은 `--min-page-count 101`로 표현한다.
- 기본값은 `1`로 두어 기존 `ocr-overlay-batch` 호출의 대상 선택 결과를 유지했다.
- 같은 설정을 Python public interface에서도 사용할 수 있도록 `OcrOverlayBatchConfig.min_page_count`를 추가하고, bool이 아닌 1 이상의 정수인지 검증한다.
- 기준 미달은 단순 skip으로 숨기지 않고 `target_reject_reason`에 `below_min_page_count`와 실제/설정 page 수를 기록하도록 했다.

## 작동 방식

- CLI가 `--min-page-count`를 `OcrOverlayBatchConfig`로 전달한다. Typer는 1 미만 값을 parser 단계에서 거부하고, Python API는 dataclass 생성 시 같은 범위를 검증한다.
- batch 사전 분류에서 `classify_scan()`이 반환한 전체 `page_count`와 최소값을 비교한다. 최종 target은 `scan.is_scanned`, meaningful bookmark 없음, 최소 page 수 충족을 모두 만족해야 한다.
- 기준 미달 PDF는 OCR builder를 호출하지 않으며 dry-run/실행 report 모두에 `below_min_page_count: page_count=<actual> < min_page_count=<configured>`를 남긴다.
- `--min-page-count`는 PDF의 전체 page 개수에 대한 조건이며, scan 판정용 `--max-sample-pages`와는 독립적이다.

## 대안과 제외한 선택지

- `--min-pages 100`을 "100쪽 초과"로 해석하는 exclusive interface는 경계 의미가 모호해 제외했다. 일반적인 최소값 의미를 따르는 inclusive `--min-page-count 101`이 자동화에서 더 명확하다.
- PowerShell로 page 수를 조사해 별도 입력 디렉터리를 만드는 방식은 public interface 밖의 staging 작업과 파일 복제를 요구하므로 제외했다.
- `classify-scan`에도 같은 옵션을 동시에 추가하는 방안은 이번 요구 범위가 OCR batch 대상 제한이므로 포함하지 않았다.

## 남은 리스크

- `--min-page-count`는 현재 `ocr-overlay-batch`에만 있다. 독립 분류 report에서도 같은 필터가 필요해지면 `classify-scan`과 공통 selection config를 도입해야 한다.
- 기존 bookmark의 low-quality 판정과 포함 정책은 아직 이 필터와 별개다. low-quality bookmark까지 OCR 대상으로 포함하는 public policy는 후속 구현이 필요하다.
- reject reason은 현재 하나의 대표 사유만 기록하므로, 여러 조건을 동시에 만족하지 못한 PDF의 모든 제외 근거가 필요하면 구조화된 reason 목록으로 확장해야 한다.
