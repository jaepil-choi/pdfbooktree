## 변경 배경

- `ocr-overlay-batch`에 `.\data\300STUDY` 같은 상대 입력 경로를 전달하면 PDF
  탐색 직후 첫 파일 분류에서 `Path.relative_to()`가 실패했다.
- 공용 `discover_pdfs()`는 입력 루트를 `resolve()`한 뒤 절대 PDF 경로를
  반환하지만, `OcrOverlayBatchRunner`는 CLI에서 받은 상대 입력 루트를 그대로
  보관했다. 이 때문에 서로 다른 경로 기준을 비교했고, 파일별 분류 예외 처리에
  진입하기 전에 batch 전체가 중단됐다.
- 같은 탐색기와 상대 경로 계산을 사용하는 `ScanBookmarkClassifier`에도 동일한
  결함이 있어 함께 수정했다.

## 결정 내용

- OCR batch와 scan/bookmark classifier가 생성될 때 `input_dir`과 `output_dir`을
  모두 절대 canonical path로 정규화한다.
- CLI와 Python API의 입력 형식은 변경하지 않는다. 상대 경로와 절대 경로를
  계속 허용하고, runner 내부 경로 기준만 통일한다.
- `discover_pdfs()`의 절대 경로 반환 계약과 원본 상대 경로를 보존하는 output
  배치 규칙은 유지한다.

## 작동 방식

- runner 생성 시 `Path(config.input_dir).resolve()`와
  `Path(config.output_dir).resolve()`를 한 번 수행한다.
- PDF 탐색 결과와 `self.input_dir`이 같은 절대 경로 기준을 사용하므로
  `pdf_path.relative_to(self.input_dir)`가 정상적으로 원본 하위 경로를 만든다.
- 계산된 상대 POSIX 경로는 기존과 동일하게 `pdfs/`와 `artifacts/` 아래 output
  위치 및 CSV/JSONL report의 `relative_path`에 사용된다.
- PDF 자체의 scan/bookmark 판정 실패는 기존 파일별 예외 처리에 남고, 경로
  기준 불일치로 batch 준비 단계 전체가 중단되는 문제만 제거한다.

## 대안과 제외한 선택지

- 사용자에게 항상 절대 경로를 전달하도록 요구하는 방법은 CLI가 `Path` 상대
  경로를 정상 입력으로 허용하는 계약을 깨고 Python API 결함을 남기므로
  제외했다.
- `discover_pdfs()`가 상대 경로를 반환하도록 바꾸는 방법은 다른 batch
  consumer와 manifest의 절대 경로 계약에 영향을 주므로 제외했다.
- `relative_to()`만 파일별 `try` 안으로 이동하는 방법은 잘못된 경로 기준을
  정상화하지 않고 invariant 위반을 개별 PDF 오류로 숨기므로 제외했다.

## 남은 리스크

- `Path.resolve()`는 symlink가 포함된 경로를 실제 위치로 canonicalize한다.
  다만 PDF 탐색기가 이미 같은 처리를 사용하므로 이번 변경은 두 경로 기준을
  기존 탐색 계약에 맞춘 것이다.
- 1,245개 실제 사용자 데이터 전체의 dry-run은 수행하지 않았다. 파일별 PDF
  parser 오류는 기존 report의 `failed` 항목으로 계속 확인해야 한다.
