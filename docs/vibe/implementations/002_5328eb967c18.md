## 변경 배경

- 실험 003은 기존 bookmark를 기준 신호로 쓰는 TOC page 복원 흐름과, bookmark 없이 제품 처리에서 사용할 수 있는 TOC page feature/segment 흐름이 섞여 있었다.
- 다음 구현에서 이 둘을 한 파일에 넣으면 기본 처리 경로가 기존 bookmark에 의존하는지 구분하기 어려워진다.
- 사용자는 `silver label` 같은 평가 단계 용어보다 입력 계약이 직접 드러나는 이름을 원했고, metric 계산은 TOC 탐지 모듈보다 별도 metric 모듈에 두는 편이 더 명확하다고 판단했다.

## 결정 내용

- `toc.detect`는 bookmark 없이 page feature만으로 TOC page range를 찾는 기본 detector 진입점으로 남겼다.
- `toc.detect_from_bookmarks`를 추가해 기존 bookmark title을 기준 신호로 사용하는 TOC page range 복원 흐름을 분리했다.
- `toc.segments`를 추가해 page score에서 연속 TOC segment 후보를 만들고 선택하는 책임을 둘 자리를 마련했다.
- `metrics.toc_pages`를 추가해 IoU, start/end error, precision/recall 같은 채점 책임을 TOC 탐지 코드에서 분리했다.
- `BatchResult.silver_label_candidate_count`는 `bookmark_reference_candidate_count`로 바꿔 코드 용어에서 평가 단계 이름을 제거했다.
- `CLAUDE.md`는 사용자의 요청에 따라 `@AGENTS.md`를 가리키는 위임 파일로 함께 커밋했다.

## 작동 방식

- 현재 `detect_toc_pages()`는 구현 전 scaffold 상태를 명확히 드러내기 위해 빈 TOC page 결과와 입력 page 후보만 반환한다.
- `Processor`는 기존처럼 `toc.detect.detect_toc_pages()`를 호출하므로 public processing flow의 import 경계는 유지된다.
- 새로 추가한 `detect_from_bookmarks`, `segments`, `metrics.toc_pages`는 실제 알고리즘을 담지 않고 파일 단위 역할과 책임만 한글 문서 문자열로 남긴다.
- 모든 새 모듈의 책임 설명은 1-based page number convention을 전제로 한다.

## 대안과 제외한 선택지

- `evaluation/silver_labels` 같은 하위 패키지를 만드는 방법은 제외했다. 현재 단계에서는 TOC 도메인 안에 bookmark 기반 detector를 두는 편이 더 직관적이다.
- `toc.compare`를 만드는 방법도 제외했다. 비교와 채점은 metric 계산이므로 `metrics.toc_pages`가 더 적절하다.
- `toc.detect` 안에 bookmark 기반 탐지를 함께 넣는 방법은 제외했다. 같은 detector 이름 아래 두 입력 계약을 섞으면 제품 기본 경로의 의존성이 흐려질 수 있다.

## 남은 리스크

- `detect_toc_pages()`는 의도적으로 실제 탐지를 수행하지 않는다. 다음 구현에서 실험 003의 runtime-safe segment scoring을 채워야 한다.
- `detect_from_bookmarks`도 아직 기존 bookmark title과 page text를 연결하지 않는다.
- metric 함수는 아직 빈 scaffold다. 다음 구현에서 작은 순수 함수부터 테스트와 함께 채워야 한다.
- implementation note 생성 스크립트의 format 오류는 별도 script 작업으로 고칠 필요가 있다.
