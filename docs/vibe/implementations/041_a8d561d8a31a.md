## 변경 배경

- showcase 014(수리통계학 개정판, 637쪽)를 점검하다가 OCR invisible text layer의
  `get_text()` 문자 커버리지가 44.3%에 불과함을 발견했다. `overlay_mode="element"`
  fallback(문단/표 전체를 line 하나로 합침)을 [insertion.py](../../../src/pdfbooktree/ocr/insertion.py)가
  폭 제한 없이 한 줄로 삽입해서, 렌더링 폭이 page 폭을 크게 넘고 PyMuPDF
  `get_text()`가 page 밖 glyph를 추출하지 않아 그만큼 사라졌다.
- 사용자가 "Upstage Document Parse로 받아온 데이터는 모두 PDF page에 embed되어야
  하고, loss가 있으면 안 된다"고 명시적으로 요구해서 부분 개선이 아니라 100%
  보장을 목표로 재조사했다.
- `experiments/086_element_overlay_wrap_coverage.py`에서 element 모드만 bbox 폭
  기준 word-wrap하면 44.3% -> 79.5%로 개선되지만 277개 page가 여전히 80% 미만임을
  확인했다.
- `experiments/087_zero_loss_overlay_wrap.py`에서 남은 손실의 두 원인을 규명했다.
  1. wrap이 `overlay_mode="element"`에만 적용돼 word/row 모드는 substitute
     font(malgun.ttf)가 원본 OCR bbox보다 넓게 렌더링되면 그대로 잘렸다.
  2. 90/270도 회전된 page(637쪽 중 3쪽) 에서 `get_text()`가 TextWriter가 쓰는
     회전 반영 `page.rect`가 아니라 회전 미반영 원본 MediaBox 크기로 clip한다는
     PyMuPDF 동작을 fitz로 직접 재현해 확인했다(mediabox와 page.rect는 90/270도
     회전에서 width/height가 서로 바뀐다).

## 결정 내용

- `overlay_mode`로 분기하지 않고 **모든 line**에 동일한 fit-or-wrap 로직
  (`_fit_line_text`)을 적용한다. 자연 font_size(`rect.height*0.88`)로 한 줄에
  들어가면 기존과 동일하게 한 줄만 쓰고(대다수의 정상 line, 성능 회귀 없음),
  안 들어가면 word-wrap 후 font_size를 줄여 다시 맞춘다.
- font_size를 줄일 fitting 대상은 **line의 top부터 page 하단까지** 남은 공간
  전체(`safe_bounds`)로 삼는다. bbox 자체 높이로 제한하면 텍스트가 아주 많은
  element(예: 페이지 1의 5,405자)가 못 들어갈 수 있기 때문이다.
- font_size 탐색은 이분 탐색(`BINARY_SEARCH_ITER=30`)으로 바꿨다. 첫 시도(086)는
  `rect.height/line_count`로 매 반복 재계산하는 방식이라 font_size가 다시 커지는
  진동(oscillation)이 있었고, 페이지 1/457이 1% 미만 커버리지로 남는 원인이었다.
  이분 탐색은 "이 font_size로 wrap+height+width가 다 들어가는가"를 판정만 하므로
  진동 없이 단조 수렴한다.
- fitting에 쓰는 안전 영역(`safe_bounds`)은 `page.rect`가 아니라
  `fitz.Rect(0, 0, page.mediabox.width, page.mediabox.height)`로 계산한다.
  회전이 0/180도면 mediabox == page.rect라 차이가 없고, 90/270도면
  `get_text()`가 실제로 clip하는 (더 좁은) 영역과 일치시킨다.
- `MIN_FONT_SIZE_PT`/`MAX_FONT_SIZE_PT`(가독성 목적의 페이지 비례 clamp)는
  그대로 두고, zero-loss fitting 전용으로 `FIT_MIN_FONT_SIZE_PT = 0.05`를
  별도로 뒀다. invisible layer라 극단적으로 작은 font_size도 시각적으로는
  문제 없고, 이 하한 덕분에 "wrap_width>0, available_height>0이면 항상 들어갈
  font_size가 존재한다"는 수학적 보장(단어 폭이 font_size에 선형 비례)이 실질적으로
  성립한다.

## 작동 방식

1. `_insert_invisible_lines`가 page마다 `safe_bounds`를 한 번 계산한다.
2. element의 각 line마다 `_scale_rect`로 OCR bbox를 page 좌표계(pt)로 변환한다.
3. `_fit_line_text(font, text, rect, safe_bounds, min_font_size, max_font_size)`를
   호출한다.
   - 자연 font_size로 만든 단일 줄이 `wrap_width` 이내면 그 한 줄 그대로 반환한다
     (원래 코드와 동일 동작, 대부분의 line이 여기서 끝난다).
   - 아니면 `FIT_MIN_FONT_SIZE_PT`~자연 font_size 구간에서 이분 탐색한다. 각
     후보 font_size마다 `_wrap_words_to_width`로 word 단위 greedy wrap을 만들고,
     `_fits_within_bounds`로 (a) 줄 수 * font_size * 줄간격이 available_height
     이내인지, (b) 가장 넓은 줄의 렌더 폭이 wrap_width 이내인지를 함께 확인한다
     (단일 초과 토큰이 있어도 font_size를 줄이면 결국 통과한다).
4. 반환된 wrapped_lines를 `origin_y0`(= line bbox 상단, safe_bounds 안으로
   clamp)부터 아래로 줄 간격만큼 쌓아 `TextWriter.append`한다. x 시작점도
   safe_bounds 폭 안으로 clamp한다.
5. `write_text(page, overlay=True, render_mode=3)`으로 invisible text로만
   삽입하므로 시각적 렌더링은 그대로다(회전 페이지 포함, 실험에서 pixel hash로
   확인).

## 대안과 제외한 선택지

- **element 모드만 wrap(086의 1차 구현)**: word/row 모드의 font 대체 폭 불일치와
  회전 page 문제를 못 잡아서 기각.
- **shrink 비율 재계산(`rect.height/line_count`) 방식**: font_size가 진동해서
  페이지 1/457 같은 극단 케이스에서 수렴하지 않았다. 이분 탐색으로 교체.
- **wrap 폭을 항상 page 전체 남은 폭으로 넓힘**: bbox 폭이 이미 시각적 컬럼
  경계를 반영하므로, 폭은 bbox 그대로 두고 font_size만 줄이는 쪽을 택했다(수학적으로
  font_size를 충분히 줄이면 어떤 wrap_width>0에서도 결국 들어간다).
- **회전 대응으로 `page.set_rotation(0)` 후 삽입**: page 자체의 회전 속성을
  바꾸는 것은 원본 PDF의 표시 방식을 변경하는 부작용이 있어 배제하고, fitting
  계산에서만 MediaBox 기준으로 보정했다.

## 남은 리스크

- 637쪽 book 기준 처리 시간이 baseline 15초에서 약 270초로 늘었다. 모든 line에
  대해 "자연 font_size로 들어가는가"를 먼저 싸게 확인하고 안 들어갈 때만 이분
  탐색하도록 fast path를 뒀지만, element 모드처럼 원래도 안 들어가던 line이 많은
  book에서는 이분 탐색 비용이 누적된다. 더 큰 book이나 배치 처리 시 성능을
  재측정할 필요가 있다.
- `page.mediabox`를 안전 영역으로 쓰고 `page.cropbox`는 별도로 확인하지 않았다.
  이번 대상 book은 cropbox == mediabox였지만, 둘이 다른 PDF(예: 인쇄 여백을
  자른 스캔본)에서는 추가 검증이 필요할 수 있다.
- wrap은 순수 word 단위 greedy 방식이라 표의 행/열 구분이나 원래 줄바꿈 의미를
  보존하지 않는다. 검색/복사 가능한 문자 보존이 목표라 이 구현에서는 허용했지만,
  구조 보존이 필요한 후속 기능(예: 표 기반 목차 추론)에는 별도 처리가 필요하다.
