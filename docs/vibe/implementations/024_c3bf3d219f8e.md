- 구현 노트 022에서 `Processor(use_llm=True)`가 LLM range fallback과 item extraction까지
  연결됐지만, item extraction은 여전히 텍스트만 넘기는 기본 `LlmTocExtractor`였다. 이 경로는
  한국어 OCR 목차처럼 장/절 구분이 글씨 크기에 의존하는 책에서 level을 평탄화하거나, 깨진
  OCR 줄을 누락하는 문제가 남았다.
- experiment 017은 TOC line의 span bbox height만으로 1D tier를 안정적으로 복원할 수 있음을
  보였다. 특히 `algorithms_to_live_by`는 큰 글씨 장 제목 11줄과 작은 글씨 항목 tier가 분리됐다.
- experiment 021은 "tier 수와 tier->level 매핑은 코드가 고정하고, LLM은 page별로 tier/title/page만
  반환"하는 staged 방식으로 순서, 누락, 계층 일관성을 복구했다. `algorithms_to_live_by`에서
  `{L1: 11, L2: 100}` 구조가 나왔고, 이 실험 결과를 runtime 기본 fallback으로 이식할 필요가 있었다.
- 사용자가 implementations/showcase/experiments를 검토한 다음 작업으로 staged size-aware extractor
  이식을 승인했고, 이식 뒤 showcase 006으로 실제 품질을 다시 확인하라고 요청했다.

## 결정 내용

- 새 모듈 `toc/staged_llm_extract.py`를 추가했다. `SizeAwareStagedTocExtractor`는 기존
  extractor와 같은 `extract(pdf_path, toc_pages)` public interface를 제공해 `Processor`에 자연스럽게
  주입될 수 있게 했다.
- `TocVisualLine` dataclass를 추가해 TOC page의 `pdf_page`, 대표 `height`, `text`를 명시적으로
  전달한다. 기존 `PdfPageText`는 plain text 전용이라 글씨 높이 정보를 담기 어렵고, 이 기능의 핵심
  신호를 숨기지 않는 별도 모델이 낫다고 판단했다.
- `ProcessingConfig.llm_item_extraction_strategy`를 추가하고 기본값을 `"staged"`로 뒀다. 기존
  `LlmTocExtractor` 경로는 `"basic"`으로 남겨 호환성과 비교 가능성을 유지했다.
- staged extractor 설정은 `LlmStagedTocExtractionConfig`로 분리했다. 모델, endpoint, timeout,
  token, confidence, schema/extract prompt를 별도 설정으로 노출해 기존 `LlmTocExtractionConfig`와
  역할을 섞지 않았다.
- experiment 017의 SciPy KDE를 그대로 제품 의존성으로 가져오지 않고, 이미 runtime dependency인
  `numpy`만으로 Gaussian density와 local maxima/minima를 계산했다. 의존성을 늘리지 않으면서
  실험의 "k를 고정하지 않고 density valley를 cut으로 사용"하는 의도를 유지했다.
- LLM이 structured output에서 tier를 잘못 복사하는 경우를 줄이기 위해 postprocess 보정을 넣었다.
  추출 title이 같은 page의 visual line과 충분히 유사하면, LLM tier 대신 PyMuPDF에서 읽은 원문 line
  height tier를 신뢰한다. 이는 계층 판단을 코드가 소유한다는 experiment 021의 원칙을 runtime에서도
  지키기 위한 보정이다.
- `showcase/006_verify_toc_tree_and_content.py`는 새 `SizeAwareStagedTocExtractor`를 직접 사용하게
  바꿨고, showcase 기록은 live 실행 결과로 갱신했다.

## 작동 방식

- 모든 PDF page 번호는 기존 규칙과 동일하게 1-based다.
- `extract_toc_visual_lines(pdf_path, toc_pages)`는 PyMuPDF `page.get_text("dict")`에서 line별 span을
  순회한다. 한글 또는 라틴 2글자 이상이 있는 span만 content span으로 보고, line의 대표 height는
  content span bbox height의 최댓값으로 둔다. 순수 숫자, 불릿, 구분자만 있는 line은 버린다.
- `cluster_height_cut_points`는 height 배열에서 Gaussian density를 만들고 봉우리 사이 골짜기를
  cut point로 잡는다. `assign_tier`는 큰 글씨를 T1, 그다음 글씨를 T2...로 매핑한다.
- `content_tier_to_level`은 `목차`, `Contents`, `Brief Contents` 같은 page 머리말 단독 줄을 제외한
  content tier만 level로 매핑한다. 큰 글씨 tier가 level 1이다.
- 1단계 LLM 호출은 첫 TOC page의 `[Tn] line`과 고정된 tier 수를 받아 hierarchy schema의 level 이름,
  cue, example만 정한다. response schema의 `minItems/maxItems`로 level 수를 고정한다.
- 2단계 LLM 호출은 각 TOC page를 독립적으로 처리한다. LLM은 `{tier, title, printed_page}`만 반환하고
  level은 반환하지 않는다. 코드는 `tier_to_level`로 최종 `TocItem.level`을 부여한다.
- `Processor._extract_items_with_llm`는 주입 extractor가 없고 `use_llm=True`이면 기본적으로
  `SizeAwareStagedTocExtractor`를 lazy 생성한다. `llm_item_extraction_strategy="basic"`이면 기존
  `LlmTocExtractor`를 사용한다.

## 대안과 제외한 선택지

- 기존 `LlmTocExtractor` prompt만 강화하는 방식은 제외했다. 실험 018/020에서 prompt만으로는 장 제목
  누락이나 순서 붕괴가 반복됐고, 계층 판단을 LLM에 맡기는 구조 자체가 문제였다.
- LLM이 level을 직접 반환하게 하는 방식도 제외했다. staged 설계의 핵심은 LLM이 tier만 복사하고
  level은 코드가 결정하는 것이므로, level 출력은 같은 오류 경로를 다시 열어 둔다.
- SciPy `gaussian_kde`를 runtime 의존성으로 추가하는 방식은 제외했다. 실험에는 적합했지만 제품
  코드에서는 의존성을 늘리지 않고 `numpy`로 충분히 재현할 수 있었다.
- 새 Processor 옵션 없이 기본 extractor를 곧장 교체하는 방식은 부분적으로만 택했다. 기본값은
  staged로 바꾸되, `llm_item_extraction_strategy="basic"`으로 기존 동작을 보존했다.

## 남은 리스크

- OCR 제목 복원은 여전히 LLM 품질에 의존한다. showcase 006에서 계층은 `{1: 11, 2: 100}`으로 복구됐지만
  `가장최신의것`, `주처할 때`, 일부 깨진 한자/기호 노이즈는 남는다.
- source grounding은 `algorithms_to_live_by`에서 110/111로 높지만 완전하지 않다. OCR 복원된 제목이
  원문 깨진 텍스트와 매칭되지 않는 경우가 있어, grounding metric 자체도 OCR 복원 친화적으로 개선할
  여지가 있다.
- body spot-check는 `algorithms_to_live_by`에서 0/8로 낮다. 이는 staged extractor보다 offset/heading
  alignment와 본문 heading OCR 품질 문제에 가깝고, 후속으로 heading alignment 튜닝이나 manual offset
  경로가 필요하다.
- `algorithm_nine`은 offset fast-fail이 계속 발생한다. TOC range/item은 성공하지만 전체 content pipeline
  검증은 수동 offset override가 생기기 전까지 막힌다.
- density cut은 sample에서 안정적이지만, 글씨 크기 차이가 작거나 OCR span height가 들쭉날쭉한 PDF에서는
  tier가 과분할/과소분할될 수 있다. 필요하면 최소 peak 간격, 최소 tier support 같은 후처리를 추가해야 한다.
