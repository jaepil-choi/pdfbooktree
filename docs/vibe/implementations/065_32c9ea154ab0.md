## 변경 배경

- 기본 Markdown tree는 progressive graph로 전환됐지만 length-limited split은
  output root의 flat Markdown 파일과 `manifest.json`을 계속 사용했다. 같은
  `MarkdownExportResult`가 export mode에 따라 YAML, node identity, navigation,
  evidence와 validation 의미가 달라 agent가 별도 parser와 탐색 흐름을 가져야 했다.
- 실험 `105_markdown_split_graph_contract`에서 실제 Shreve PDF 349쪽과 기존 outline
  238개를 `max_words=10000`, coverage 0.95로 비교했다. 선택 level 1의 split
  boundary 34개를 graph로 만들었을 때 YAML 35개가 모두 parse됐고 dangling link와
  duplicated page가 0개였으며 graph validation이 통과했다.
- 릴리스 전 요구사항은 tree와 split에서 source, confidence, evidence reference를
  잃지 않고 node 파일을 모두 열기 전에 manifest에서 관계와 page coverage를
  조사할 수 있는 공통 계약을 요구한다.

## 결정 내용

- split output도 `<stem>_markdown_split/` 아래 `toc.md`, `bookmark_plan.json`,
  `nodes/`, `markdown_manifest.json`을 가진 graph로 변경했다. manifest는
  `export_mode=split`, node front matter는 `content_mode=bounded`를 사용한다.
- 선택된 boundary에 새 연속 번호를 부여하지 않고 원래 plan의 global order를
  `n####` node ID와 filename prefix에 사용한다. 따라서 선택 level이 달라져도 같은
  plan item은 같은 identity와 `bookmark_plan.json#n####` evidence reference를 갖는다.
- 각 split node는 `contained_plan_node_ids`로 자신이 묶은 원 plan 범위를 기록한다.
  관계 graph는 export된 boundary끼리만 parent/children/previous/next를 계산한다.
- 같은 PDF page에서 boundary가 연속되면 tree direct mode와 마찬가지로 마지막
  export node만 page 본문을 소유하고 앞선 node는 navigation-only로 만든다.
- max-word 선택은 기존 의미를 유지했다. heading과 PDF 본문만 word count에
  포함하고 새 front matter, navigation, page marker는 제한 계산에서 제외한다.
- `inspect_plan_artifact()`는 report, run manifest, 직접 경로와 output 하위 검색
  순서로 `markdown_manifest.json`을 찾고 schema, export mode, 선택 level,
  validation, coverage와 manifest warning 요약을 반환한다.
- package에 번들된 `use-pdfbooktree` skill 계약도 새 split/inspect 의미로
  갱신했다. repo-local skill 동기화는 별도 문서 커밋에서 수행한다.

## 작동 방식

- `export_markdown_split()`은 level별 boundary document와 word-count coverage를 먼저
  계산하고 가장 얕은 충족 level 또는 가장 깊은 fallback level을 선택한다. 선택된
  document를 `MarkdownSplitGraphDocument`로 변환해 원 plan order, bounded page
  범위, content Markdown, word count와 contained node ID를 전달한다.
- `export_markdown_split_graph()`는 node 관계를 연결하고 full plan snapshot,
  Obsidian wiki-link TOC, YAML node 파일과 canonical manifest를 쓴다. 이전 0.1.0
  이전 flat split filename과 `manifest.json`이 같은 generated directory에 남아
  있으면 알려진 legacy pattern만 제거한다.
- 공통 graph validator는 YAML parse, node/path 중복, dangling link,
  parent/children 및 previous/next 대칭, root reachability, TOC link, page 중복과
  mapping 결정성을 확인한다. bounded/direct mode에서는 duplicated page가 하나라도
  있으면 실패 manifest를 남긴 뒤 `RuntimeError`를 발생시킨다.
- 모든 `pdf_page`, `pdf_start_page`, `pdf_end_page`, content page 범위는 외부 계약과
  동일하게 1-based다. 첫 boundary 전 page는 unassigned coverage로 기록한다.
- `inspect plan`은 manifest 전체 node 배열을 반환하지 않고 검토 시작에 필요한
  요약만 제공하므로 큰 책에서도 node 파일을 scan하지 않고 다음 조사 위치를
  선택할 수 있다.

## 대안과 제외한 선택지

- split boundary를 `s0001`부터 다시 번호 매기는 방식은 file 수는 단순하지만 tree와
  split 사이에서 plan identity와 evidence reference가 달라져 제외했다.
- 기존 flat split에 front matter만 추가하는 방식은 TOC reachability, 관계 link와
  공통 graph manifest를 제공하지 못해 제외했다.
- navigation과 page marker까지 max-word 계산에 넣는 방식은 artifact 표현을 바꾸는
  것만으로 chosen level이 2에서 3으로 변하는 회귀 테스트가 발생해 제외했다.
- same-page boundary마다 같은 page text를 복제하는 방식은 bounded graph의 page
  coverage와 retrieval 중복 제거 목표를 깨므로 제외했다.
- 모든 full plan item을 split graph node로 export하는 방식은 length-limited
  boundary 선택 결과와 file count 의미를 없애므로 선택된 boundary만 node로 만들고
  나머지는 `contained_plan_node_ids`에 기록했다.

## 남은 리스크

- 같은 page의 여러 heading을 page 내부 geometry로 나누지 않으므로 마지막 boundary가
  앞선 section text까지 소유할 수 있다. 현재 manifest의 same-page warning을 review
  signal로 사용해야 한다.
- split node의 parent/children은 export된 boundary graph 기준이다. 포함된 더 깊은
  plan item의 개별 관계와 evidence를 보려면 `contained_plan_node_ids`를 따라
  `bookmark_plan.json`을 확인해야 한다.
- `inspect plan`은 이번 단계에서 manifest summary만 제공한다. item ID, page range,
  source와 attention signal filter는 후속 bookmark review evidence phase가 필요하다.
- 전체 Ruff lint/format, 동작하지 않는 `ocr_policy=auto|always`, LICENSE/PyPI metadata와
  wheel smoke test는 여전히 0.1.0 릴리스 blocker다.
- Windows에서 실행 중인 `.venv\\Scripts\\pdfbooktree.exe`가 environment sync를
  잠글 수 있어 이번 검증은 설치된 environment에 `--no-sync`를 사용했다. 최종 wheel
  검증 전에는 해당 프로세스를 종료하고 정상 sync/install smoke test가 필요하다.
