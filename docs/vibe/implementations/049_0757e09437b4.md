## 변경 배경

- `docs/handoff/agent-friendly-interface-roadmap.md` 5.7은 `infer`/`apply` CLI를 Phase 2의 남은 조건으로 남겨뒀다: `infer`는 plan과 근거 artifact만 만들고 bookmarked PDF/Markdown은 만들지 않아야 하고, `apply`는 기존 plan을 읽어 최종 산출물만 만들며 typography extraction을 다시 실행하지 않아야 한다.
- 직전 커밋(`f2d801675acc`, `048_f2d801675acc.md`)이 만든 `resolve_existing_outline_action()`(existing-outline quality policy)을 `Processor`만 쓰는 채로 두면 `infer` CLI가 같은 정책을 다시 구현하게 되어 drift 위험이 생긴다. 이 커밋은 그 정책을 `infer`에도 그대로 연결한다.

## 결정 내용

- `outline/plan_io.py`를 새로 만들어 `load_bookmark_plan_json(path) -> list[BookmarkPlanItem]`과 `PlanError`를 정의했다. `outline/plan.py`(순수 조립 로직)와 분리한 이유는 `config.py`/`config_io.py`의 로직-I/O 분리 관례를 그대로 따르기 위해서다. `title`(비어있지 않은 str), `level`/`pdf_page`(bool이 아닌 int), `source`/`confidence`/`evidence`(선택, 타입 검증)를 각 항목마다 검사하고 실패하면 몇 번째 항목의 어떤 field가 문제인지 명시한 `PlanError`를 던진다.
- `Processor._write_artifacts`가 하던 7종 artifact 저장 로직을 `artifacts.write_inference_artifacts(output_dir, inference, quality=None)`로 승격했다. `Processor`와 `infer` CLI가 같은 artifact 이름·파일로 저장하도록 강제하기 위함이다. `Processor._write_artifacts`는 이제 이 함수를 호출하는 한 줄짜리 래퍼다.
- `ConfidenceSummary` 계산도 같은 이유로 `pipeline.confidence_summary_for_inference(inference)`로 뽑았다. `Processor.run()`과 `infer`의 typography 경로가 같은 공식(`_mean`/`_tiering_confidence`, 이제 `pipeline.py` 안의 private 함수)을 쓴다.
- `RunManifest`에 `plan_source: dict[str, str] | None = None`을 추가했다(로드맵 5.5). `RunContext.record_plan_source(path, sha256)`을 새 public 메서드로 추가해 `apply`가 사용한 plan 파일의 경로와 SHA-256을 기록한다. schema_version은 올리지 않았다 - Phase 1 note가 이미 "run manifest는 versioned이지만 모든 필드가 독립 schema version을 가진 것은 아니다"라고 명시했고, 이 field는 optional·backward-compatible이다.
- `infer`/`apply` CLI는 `process`와 같은 패턴(`resolve_processing_config` -> `create_run_context`/`--flat-output` 분기 -> `run.start()` -> 실행 -> `run.complete(result)`)을 그대로 따른다. 다만 `process`처럼 legacy 개별 CLI flag(`--heading-candidate-mode` 등)는 추가하지 않고 `--config`/`--set`만 지원한다 - 로드맵 5.7 예시 인터페이스가 그렇게 되어 있고, typography field가 20개가 넘어 legacy flag를 복제하면 `--help` 발견성이 나빠진다(Phase 1 note가 이미 이 판단을 내렸다).
- `infer`가 기존 outline을 재사용할 때의 `ProcessingResult.status`로 기존에 정의만 되어 있고 쓰이지 않던 `"skipped"`(`ProcessingStatus` Literal의 세 번째 값)를 처음 사용했다. `Processor`는 이 경로에서도 "processed"를 썼지만(Markdown export가 실제로 일어나므로), `infer`는 PDF/Markdown을 아예 만들지 않는 경로라 "재사용했을 뿐 아무것도 만들지 않았다"는 걸 `status`로 구분하는 게 더 정확하다고 판단했다.

## 작동 방식

- `_run_infer(pdf, output_dir, config)`: `total_pages`를 읽고 `resolve_existing_outline_action()`을 호출한다. `reuse_existing`이면 `outline_to_plan()` + `validate_bookmark_plan()`만 하고 `existing_outline_plan`/`bookmark_plan_validation`/(quality가 있으면) `existing_outline_quality` artifact만 쓴다 - `analyze_pdf`/`infer_bookmarks`는 아예 호출되지 않는다. 아니면 `analyze_pdf` -> `infer_bookmarks` -> `write_inference_artifacts`로 진행하고 `status`는 `validation.valid` 여부로 `processed`/`failed`를 정한다. 두 경로 모두 `write_processing_report()`로 report를 남긴다. `output_pdf`/`output_markdown_dir`는 항상 `None`이다.
- `_run_apply(pdf, output_dir, plan, config)`: `total_pages`만 읽고(추출 없음) `apply_plan()`을 호출한다. `apply_plan()` 자체가 이미 typography 관련 함수를 import조차 하지 않으므로 "다시 추출하지 않는다"는 보장은 함수 경계에서 구조적으로 성립한다. `bookmark_plan_validation` artifact만 추가로 쓴다.
- `apply` CLI 명령은 `run.start()` 이후 `_run_apply()`가 성공하면 `run.record_plan_source(plan_path, file_sha256(plan_path))`을 `run.complete(result)` 전에 호출해 manifest에 남긴다. `--flat-output`에서는 manifest 자체가 없으므로 plan_source도 기록되지 않는다.
- CLI `--flat-output` 경로에서는 `RunContext` 없이 `_run_infer`/`_run_apply`가 직접 `output_dir`에 쓴다. 아닌 경로에서는 `create_run_context()`가 만든 `run.run_dir`에 쓴다 - `process`와 완전히 같은 패턴이다.

## 대안과 제외한 선택지

- `infer`/`apply`에 `process`의 legacy 개별 typography CLI flag(`--heading-candidate-mode`, `--body-font-text-coverage` 등 15개)를 복제하지 않았다. `--config`/`--set`만으로 전체 config surface에 접근할 수 있고, Phase 1이 이미 "option 수가 늘면 `--help` 발견성이 나빠진다"는 이유로 이 판단을 내렸다 - 새 명령에서 그 판단을 뒤집을 이유가 없었다.
- `apply`가 `--config`로 받는 config 전체 중 실제로 쓰는 건 `markdown_split`뿐이다. `typography`/`outline_quality`도 함께 받게 하지 않고 무시하는 대신, resolved config 전체를 그대로 받아들이는 쪽을 택했다 - `process`/`infer`와 동일한 `--config`/`--set` 계약을 유지해야 CLI 세 개가 서로 다른 config 부분집합을 요구하지 않는다. 대신 command docstring에 "markdown split 설정에만 쓰인다"고 명시했다.
- `infer`가 재사용 경로에서 만드는 결과의 `status`로 새 값을 만들지 않고 기존 `ProcessingStatus`의 `"skipped"`를 재사용했다. 새 Literal 값을 추가하면 `ProcessingResult`를 소비하는 다른 코드(예: `run.py::RunContext.complete()`의 `processing_status == "failed"` 체크)가 이 값을 몰라서 생기는 회귀 위험이 있는데, 기존 값으로 충분히 표현 가능했다.
- `experiments/102_engine_bookmark_fuzzy_eval.py`의 `_predict_plan()`을 `infer_bookmarks()` 호출로 단순화하는 작업은 이번에도 하지 않았다 - 두 증분 모두에서 반복적으로 나온 후속 과제이지만 실험 파일 변경은 이 저장소 규칙상 구현 커밋의 필수 조건이 아니다.

## 남은 리스크

- `experiments/102_engine_bookmark_fuzzy_eval.py::_predict_plan()`은 여전히 `infer_bookmarks()`를 호출하지 않고 조립 로직을 복제한다 - production 조립 순서가 바뀌면 조용히 갈라질 수 있다.
- 로드맵 Phase 2 완료조건 6개(로드맵 §5.8) 중 `apply`가 typography extraction을 호출하지 않는다는 조건은 `unittest.mock.patch`로 검증했지만, `infer`가 만든 plan과 별개로 사람이 직접 손으로 쓴 plan JSON을 `apply`에 먹이는 실사용 경로는 CLI 테스트(`test_apply_rejects_invalid_plan_json`)에서만 다뤘고 showcase에서는 다루지 않았다.
- `apply`가 받는 `--config`가 `markdown_split` 외 필드를 조용히 무시한다는 점은 코드 주석/docstring에만 있고 `--help` 출력에는 명시적으로 드러나지 않는다.
- Phase 3(공통 JSON/error envelope, exit code 정리)이 아직 없어 `infer`/`apply`의 실패 시 exit code와 stdout 포맷은 `process`와 마찬가지로 미정규화 상태다.
- `--flat-output`에서는 `plan_source`가 기록되지 않는다 - 이 조합을 쓰는 사용자는 plan 출처 추적을 포기해야 한다는 점이 문서화되지 않았다.
