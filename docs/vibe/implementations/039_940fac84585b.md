# 구현 노트: fix: preserve page identity in OCR insertable cache

- 구현 커밋: `940fac84585b`
- 전체 커밋 ID: `940fac84585b2111d38bfe3c8b92595a39ff45b2`
- 커밋 일시: `2026-07-12T17:12:05+09:00`
- 노트 생성 일시: `2026-07-12 17:12:16 +09:00`

## 변경 배경

- 실험 082에서 264개 raw OCR cache를 모두 재사용했지만 insertable cache는 263개만 남았다. 서로 다른 page가 동일한 raw OCR response를 반환하면 기존 key가 충돌해 한 page의 삽입 모델을 다른 page가 재사용할 수 있었다.
- `InsertableOcrPage`에는 1-based `pdf_page`와 해당 page의 좌표계가 포함된다. 다른 page의 모델을 재사용하면 overlay 대상 page가 누락되거나 잘못된 좌표·text가 삽입될 수 있어 OCR 전처리 산출물의 정확성을 보장할 수 없었다.
- 실제 cache와 PDF는 정리된 상태이므로, 이미 기록된 실험 082의 관측을 근거로 동일 raw response를 반환하는 두 page를 이용한 결정적 회귀 테스트를 추가했다.

## 결정 내용

- `OcrCache.insertable_cache_key()`에 `raw_cache_key`를 추가하고, key payload에 `cache_version=2`와 함께 기록했다.
- `raw_cache_key`는 입력 PDF hash, 1-based page 번호, render DPI, engine, 요청 파라미터를 이미 포함하므로 insertable 모델의 page identity를 가장 작은 변경으로 보존한다.
- `OcrOverlayBuilder`가 raw response를 조회할 때 계산한 `raw_key`를 그대로 insertable key 생성에 전달한다. public CLI와 `OcrOverlayConfig` 계약은 바꾸지 않았다.
- v1 insertable cache는 v2 key로 조회되지 않는다. raw cache가 있으면 API 호출 없이 표준 삽입 모델을 다시 생성하고, raw cache까지 없으면 기존 `cache_policy="only"` 계약대로 명시적으로 실패한다.

## 작동 방식

- builder는 page마다 raw OCR response를 읽거나 생성한 뒤, 해당 page의 `raw_key`, raw response hash, adapter version으로 insertable key를 만든다.
- raw response 내용이 빈 page처럼 같아도 `raw_key` 안의 1-based page 번호가 다르므로 insertable JSON 파일도 별도로 저장된다.
- 후속 `cache_policy="only"` 실행에서는 raw cache와 새 insertable cache를 모두 page별로 hit해 OCR API를 호출하지 않고도 올바른 `pdf_page` 순서의 overlay 입력을 복원한다.

- 새 cache key 단위 테스트는 같은 raw response라도 서로 다른 raw cache key에서 다른 insertable key가 생성되는지 확인한다.
- 새 builder 회귀 테스트는 2-page PDF에서 동일 raw response를 반환시키고, 최초 실행과 `cache_policy="only"` 재실행 모두 `[1, 2]` page 모델을 전달하며 두 번째 실행에서 OCR 호출이 없음을 확인한다.
- 실제 300STUDY cache는 정리되어 같은 책으로 live 재실행하지 못했다. 회귀는 외부 API나 local cache에 의존하지 않도록 테스트로 고정했다.

## 대안과 제외한 선택지

- raw response hash만 유지하고 `pdf_page`를 insertable JSON 내용으로 검증하는 방식은 제외했다. 충돌을 매번 발견한 뒤 재생성하는 방식보다 cache key 자체가 page identity를 표현해야 안전하다.
- 입력 PDF hash와 page 번호를 insertable key에 새로 중복 계산하는 방식은 제외했다. 이미 같은 정보를 포함하는 `raw_cache_key`를 재사용해 key 생성 규칙이 한 곳에 유지되도록 했다.
- 기존 v1 insertable cache를 파일명 변경으로 마이그레이션하는 방식은 제외했다. 충돌한 v1 cache는 어떤 page 모델이 맞는지 신뢰할 수 없으므로 raw cache에서 안전하게 재생성해야 한다.

## 남은 리스크

- 기존 v1 insertable JSON은 자동 삭제하지 않으므로 disk 공간을 계속 차지할 수 있다. cache 정리 정책이 필요해지면 별도 유지보수 작업으로 다룬다.
- raw cache가 이미 삭제된 환경에서는 `cache_policy="only"`로 v2 insertable cache를 새로 만들 수 없다. 이 경우 사용자는 `reuse` 또는 `refresh` 정책으로 OCR을 다시 실행해야 한다.
- 실제 대량 OCR cache에서의 live 재검증은 새 cache가 쌓인 뒤 showcase로 다시 수행할 필요가 있다.
