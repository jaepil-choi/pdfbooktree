## 변경 배경

- 단일 `ocr-overlay` 명령은 tqdm 기반 진행 표시를 사용하면서도 완료 후 `OcrOverlayResult` 전체를 터미널에 출력했다.
- 페이지가 많은 PDF에서는 `processed_pages` 배열이 길게 펼쳐져, batch 명령의 간결한 완료 요약과 달리 최종 출력이 지나치게 길어졌다.

## 결정 내용

- OCR 처리 결과 모델과 상세 artifact 형식은 변경하지 않고, 단일 CLI가 터미널에 보여주는 완료 요약만 축소했다.
- 완료 요약에는 상태, 전체/처리 페이지 수, cache hit/miss 수, 출력 PDF·artifact 디렉터리·페이지 통계 경로만 포함한다.
- 상세 페이지 목록과 경고 등은 기존 결과 모델과 JSON log/report에 그대로 보존하고 터미널 기본 출력에서만 제외한다.

## 작동 방식

- `OcrOverlayBuilder.run()`이 반환한 결과에서 `processed_pages`의 길이를 `processed_page_count`로 계산한다.
- CLI는 선택한 필드로 작은 사전을 구성한 뒤 기존 `to_jsonable()`과 `rich_print()` 흐름으로 출력한다.
- 진행 중에는 기존 `TqdmOcrLogger`가 페이지 완료 시에만 진행률을 갱신하며, `plain`과 `json` log mode의 명시적 동작은 바뀌지 않는다.

## 대안과 제외한 선택지

- `OcrOverlayResult` 자체를 축소하면 다른 Python 호출자와 report 생성 흐름의 공개 데이터가 손실되므로 제외했다.
- tqdm logger의 event 필터를 추가로 바꾸는 접근은 진행 중 출력이 이미 페이지 완료 기반으로 정리되어 있어 적용하지 않았다.
- 상세 결과를 별도 새 파일로 추가 저장하는 방식은 기존 OCR log와 report가 같은 역할을 하므로 중복을 피했다.

## 남은 리스크

- 경고 내용을 기본 완료 출력에서 확인할 수 없으므로 문제 조사 시 기존 `ocr_log.jsonl`, `ocr_progress.json`, `ocr_overlay_report.json`을 확인해야 한다.
- 실제 OCR API를 호출하는 live run은 수행하지 않았고 CLI 단위 테스트와 logger 테스트로 출력 계약을 검증했다.
