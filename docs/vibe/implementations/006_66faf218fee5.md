## 결정 내용

- 새 public interface로 `BookmarkTocBatchDetector`를 추가하고 패키지 root에서 export했다. 기존 `BatchProcessor`는 bookmark가 있으면 처리를 건너뛰는 생성 파이프라인이므로, bookmark가 있는 PDF만 분석하는 이번 요구와 분리했다.
- CLI에는 `detect-bookmark-toc` 명령을 추가했다. 기본값은 하위 디렉터리까지 검색하는 `--recursive`이며, 결과 저장이 필요하면 `--output-json`을 받는다.
- 결과 모델은 `BookmarkedPdfTocDetection`, `BookmarkedPdfTocBatchResult` dataclass로 분리했다. 단일 파일 결과에는 원본 경로, root 상대 경로, page 수, 읽은 text page 수, bookmark 수, TOC page, confidence, detector 원본 결과를 함께 담는다.
- diagnostic 출력은 내부 구현에 `diagnostics: Callable[[str], None] | None` callback으로 열어두고, CLI에서는 기본으로 `typer.echo`를 연결했다. 자동화나 JSON만 필요한 호출자는 `--quiet`로 끌 수 있다.
- 탐지 알고리즘은 새로 만들지 않고 기존 `detect_toc_pages_from_bookmarks`를 그대로 재사용했다. 이번 구현의 책임은 파일 탐색, bookmark 보유 PDF 선별, 파일별 detector 호출, 결과 요약, 진행 상황 보고로 한정했다.

## 작동 방식

- `BookmarkTocBatchDetector.run()`은 입력 경로가 존재하는 디렉터리인지 먼저 검증한다.
- `recursive=True`이면 `Path.rglob("*")`, 아니면 `Path.iterdir()`로 PDF 파일만 찾는다. suffix 비교는 `.PDF` 같은 대소문자 차이를 허용하기 위해 `path.suffix.lower() == ".pdf"`를 사용한다.
- 첫 번째 단계에서 모든 PDF의 기존 bookmark를 확인한다. bookmark가 없는 PDF는 결과 목록에 넣지 않고 `skipped_no_bookmark_count`만 증가시킨다.
- bookmark가 있는 PDF 목록을 확정한 뒤 파일명을 diagnostic으로 요약 출력하고, 두 번째 단계에서 각 파일을 연다.
- 각 PDF에 대해 PyMuPDF로 전체 page 수를 확인하고, `extract_page_texts(..., max_pages=max_text_pages)`로 앞부분 text layer를 읽는다. 이후 `calculate_page_features`와 `detect_toc_pages_from_bookmarks`를 호출한다.
- PDF page 번호는 기존 모델과 detector 계약을 따라 1-based 값을 유지한다.
- 파일별 예외는 전체 batch를 중단하지 않고 `status="failed"` 결과로 기록한다. bookmark 추출 실패와 TOC 탐지 중 실패 모두 파일별 error 문자열에 남긴다.
- CLI는 결과를 터미널에 출력하고, `--output-json`이 있으면 `write_json`으로 같은 결과를 JSON 파일에도 저장한다.

## 대안과 제외한 선택지

- 기존 `BatchProcessor`에 옵션을 추가하는 방식은 제외했다. 그 클래스는 bookmark/Markdown 생성 파이프라인이고 `skip_existing_bookmarks`가 핵심 동작이라, bookmark가 있는 파일을 분석 대상으로 삼는 이번 기능과 책임이 충돌한다.
- showcase 파일을 외부 경로용으로 확장하는 방식도 제외했다. 사용자는 임의 경로에 반복 적용할 public/internal interface를 원했고, showcase는 고정된 실사용 예시 검증 역할에 남기는 편이 맞다.
- diagnostic 출력을 내부에서 직접 `print`하는 방식은 제외했다. callback을 받으면 CLI 외 호출자가 메시지를 수집하거나 끌 수 있고, 테스트에서도 로그 계약을 검증할 수 있다.
- bookmark가 없는 PDF에도 기본 runtime detector를 실행하는 방식은 제외했다. 이번 요구는 bookmark가 있는 것만 뽑은 뒤 bookmark 기반 page detection을 돌리는 것이므로 범위를 좁게 유지했다.

## 남은 리스크

- 외부 드라이브의 실제 `300STUDY` 전체 실행 시간과 실패 파일 분포는 아직 이 커밋에서 기록하지 않았다. 대량 실행 후 결과 JSON을 보고 timeout, 권한, 깨진 PDF 같은 운영 이슈를 별도로 확인해야 한다.
- 현재 diagnostic은 한 줄 로그 방식이다. 아주 큰 디렉터리에서는 progress bar, 주기적 요약, 실패 로그 별도 파일이 더 편할 수 있다.
- text layer가 없거나 OCR 품질이 낮은 PDF는 bookmark가 있어도 TOC page 탐지에 실패할 수 있다.
- 결과 JSON에는 detector 원본 후보 정보가 포함되어 파일 수가 많으면 커질 수 있다. 필요하면 요약 전용 출력 옵션을 후속으로 둘 수 있다.
