- 전체 커밋 ID: `20379d5f4faaa730b1c7072f8f2bbb58b6061300`

- 노트 생성 일시: `2026-07-09 03:51:11 +09:00`

## 변경 배경

- `exp/page-order-stack-hierarchy` 브랜치의 실험 069에서 font_size 기반 whole-book heading hierarchy 알고리즘(page order상의 stack nesting으로 level을 부여)을 John Hull/Shreve 두 책에서 검증해 recall 93~99%, level accuracy 97~98%를 확인했다.
- 이 알고리즘을 실제 300STUDY OCR overlay 산출물에 적용하기 전에, invisible text layer의 font_size가 hierarchy 신호를 보존하는지 실험 070에서 확인했다. `insertion.py`가 font_size를 절대값 `[3.0, 18.0]pt`로 clamp하고 있었는데, `data/300STUDY/pdfs/a_books/normalbook`의 실제 OCR overlay 산출물 2권을 비교한 결과 source PDF의 page MediaBox가 정상 판형과 무관하게 큰 책(AB테스트_무작정따라하기, page_rect=1080x1865pt, 정상 판형의 2.5~3배)에서는 진짜 제목뿐 아니라 평범한 본문 문단(`word_height_median_pt`≈20)까지 18pt 벽에 부딪혀 heading/본문 구분 신호 자체가 사라졌다(clamp 비중 72.7%). 반면 page 크기가 정상 범위인 책(부동산대출의기술, page_rect=409x648pt)은 clamp 비중 1.4%로 문제가 거의 없었다.
- 원인은 `rect.height * 0.88`로 계산한 font_size가 page의 물리적 크기에 비례하지 않는 절대 pt 값으로 clamp된다는 것이었다. page MediaBox가 과도하게 큰 source PDF(스캔 도구의 DPI 처리 오류로 추정)에서는 body 텍스트의 bbox 높이 자체가 point 공간에서 부풀어 올라 정상적으로 18pt를 넘어버린다.

## 결정 내용

- `insertion.py`에 `MIN_FONT_SIZE_PT`(3.0), `MAX_FONT_SIZE_PT`(18.0), `REFERENCE_PAGE_HEIGHT_PT`(792.0, US Letter 세로 길이) 상수를 추가하고, `_page_relative_font_size_bounds(page_height_pt)` 헬퍼로 clamp 하한/상한을 계산하게 했다.
- scale = `max(1.0, page_height_pt / REFERENCE_PAGE_HEIGHT_PT)`로 정의해, REFERENCE_PAGE_HEIGHT_PT 이하(정상 판형)인 page는 scale=1.0이라 기존 절대 clamp `[3.0, 18.0]`과 완전히 동일하게 동작하도록 했다. 이보다 큰 page만 상하한이 비례해서 커진다.
- `rect.height * 0.88`이라는 raw font_size 계산식 자체는 바꾸지 않았다 — 이 값은 page 자체 좌표계 안에서 이미 상대적으로 올바른 시각적 크기를 반영하므로, 문제는 계산식이 아니라 절대값 clamp였다.
- CLI(`ocr-overlay` 단일 파일 명령)에 `--cache-policy`(reuse/refresh/only) 옵션을 새로 노출했다. `OcrOverlayConfig.cache_policy` 필드는 이미 존재했지만 CLI에서 설정할 방법이 없었다. `only`를 쓰면 raw/insertable cache가 없을 때 즉시 실패하고 OCR API를 호출하지 않는다 — 이번 fix를 기존 `document_parse_cache`로 재검증(API 재호출 없이 PDF만 다시 생성)하는 데 바로 필요했다.
- `ocr-overlay-batch` batch command에는 `--cache-policy`를 추가하지 않았다 — 이번 검증은 단일 파일 2권으로 충분했고, batch 쪽 plumbing(`OcrOverlayBatchConfig`에 필드 추가 + `batch.py`에서 전달)은 별도 필요 확인 후 추가하는 게 낫다고 판단했다.

## 작동 방식

- `_insert_invisible_lines`에서 `page = document[page_model.pdf_page - 1]`로 각 page의 `fitz.Page`를 얻은 직후 `_page_relative_font_size_bounds(page.rect.height)`를 한 번만 호출해 그 page의 `(min_font_size, max_font_size)`를 계산한다. page 안의 모든 line은 같은 bounds를 공유한다(문서 안에서 page 크기가 달라질 수 있으므로 page 단위로 재계산).
- 각 line을 삽입할 때 `font_size = max(min_font_size, min(max_font_size, rect.height * 0.88))`로 clamp한다. 이전에는 `min_font_size`/`max_font_size` 자리에 상수 `3.0`/`18.0`이 그대로 있었다.
- 검증은 `--cache-policy only`로 기존 `document_parse_cache`(raw + insertable 둘 다)를 그대로 읽어 OCR API 호출 없이 overlay PDF만 다시 만드는 방식으로 했다. 실제로 두 책 모두 `cache_hit_count`가 page 수와 같고 `cache_miss_count=0`이었다.

## 대안과 제외한 선택지

- `REFERENCE_PAGE_HEIGHT_PT`를 A4(841.89pt)나 두 값의 평균으로 잡는 안도 검토했지만, US Letter(792pt)를 기준으로 잡아도 정상 판형 책 대부분(<=792pt)에서 scale=1.0으로 동일하게 동작해 실질적 차이가 없었다. 정확한 기준값보다 "정상 판형은 절대 안 건드린다"는 `max(1.0, ratio)` 형태의 비대칭 스케일링이 더 중요한 설계 결정이었다.
- clamp 상하한을 대칭으로(비율 스케일 없이) 그냥 없애는 안(클램프 자체를 제거)도 고려했지만, `rect.height`가 OCR 오탐이나 여러 줄이 하나의 block으로 잘못 병합된 경우(070에서 확인한 `overlay_mode="element"`의 테이블/차트 전체 bbox) 극단적으로 커질 수 있어 상한 자체를 없애는 건 위험하다고 판단해 유지했다.
- `rect.height * 0.88` 계수 자체를 조정하는 안은 배제했다 — raw 계산식은 문제가 없었고(070의 진단에서 이미 확인), clamp 절대값만 page 크기에 비례하지 않는 게 진짜 원인이었다.

## 남은 리스크

- `ocr-overlay-batch`에는 `--cache-policy`가 아직 없다. 300STUDY 전체 배치를 이 fix로 다시 돌리려면 batch 쪽에도 cache-policy pass-through를 추가해야 한다.
- 실험 071에서 새로 드러난 문제: AB테스트_무작정따라하기처럼 이미지/차트/표/수식이 많은 책은 `overlay_mode="element"`로 삽입된 큰 bbox가 진짜 제목과 같은 tier에 섞여 heading candidate를 오염시켰다(예: `![image](/image/placeholder)...` 같은 텍스트가 최상위 tier에 낌). 이번 fix로 body/heading 구분 clamp 문제는 풀렸지만, 이 별도 노이즈 소스는 아직 손대지 않았다.
- `REFERENCE_PAGE_HEIGHT_PT=792.0`은 경험적으로 고른 값이다. 300STUDY 전체(1245개 PDF)에서 page 크기 분포를 더 넓게 확인하지 않았으므로, 정상 판형 상한 기준이 실제로 얼마나 다양한지는 후속 검증이 필요하다.
