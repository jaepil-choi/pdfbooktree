## 변경 배경

- 041(zero-loss OCR overlay fix) 작업 중 실제 CLI를 여러 번 실행해 보면서,
  기존 OCR overlay 로깅이 너무 verbose하다는 지적을 받았다. `OcrOverlayBuilder`는
  page 하나당 `page_start`/`page_render_start`/`page_render_done`/
  `ocr_call_start`/`ocr_call_done`(또는 `raw_cache_hit`)/
  `insertable_build_start`/`insertable_build_done`(또는 `insertable_cache_hit`)/
  `page_done`까지 최대 7개 event를 emit하는데, `PlainTextOcrLogger`(그리고
  stderr가 tty가 아닐 때의 기본값)는 이 event마다 한 줄씩 출력해서 page당
  6~7줄이 쏟아졌다.
- 사용자 요구사항: (1) 단일 책 처리 시 page 진행 상황을 tqdm progress bar로
  보여줄 것, (2) batch 처리 시 전체 책 중 몇 권 남았는지와 현재 책의 진행
  상황을 함께 보여주고, 남은 시간 추정은 "책 개수"가 아니라 "전체 책들의
  page 수 합"을 기준으로 할 것.

## 결정 내용

- `OcrLogMode`에서 `"rich"`를 빼고 `"tqdm"`으로 바꿨다(`Literal["tqdm", "plain",
  "json", "none"]`). `RichOcrLogger`와 `rich.progress` 의존은 완전히 제거했다.
  `default_ocr_log_mode()`는 이제 tty 여부와 무관하게 항상 `"tqdm"`을 반환한다
  (tqdm은 non-tty에서 스스로 갱신 빈도를 줄여 한 줄 출력으로 대체하므로, rich처럼
  tty 여부로 모드를 나눌 필요가 없다).
- `TqdmOcrLogger`(단일 책용)는 `event.completed_pages`가 실제로 늘어난
  순간(`page_done`)에만 `bar.update()`를 호출하고, 그 외 event는
  `bar.set_postfix(hit=..., miss=..., refresh=False)`로만 반영한다. `refresh=False`로
  둬서 postfix 갱신 자체가 매번 강제 redraw를 트리거하지 않게 했다(page당 여러 번
  호출되므로).
- batch(`OcrOverlayBatchRunner`)는 이제 `run()` 시작 시 대상 PDF 전체를
  **한 번에** 분류한다(`_classify()` 전용 메서드로 분리). 이전에는
  `_process_one()` 안에서 매 파일마다 classify와 실제 처리를 같이 했는데,
  batch 전체 page 합계를 알려면 classify를 처리보다 먼저 전부 끝내야 하고,
  이렇게 분리하면 파일별 classify를 두 번(사전 집계용 + 실제 처리용) 하지
  않아도 된다.
  - `_Classification.will_process`는 "이 책이 실제로 `OcrOverlayBuilder.run()`을
    거칠 것인가"를 미리 확정한다(target이고, dry-run이 아니고, output이 이미
    있는데 force가 아닌 경우가 아님). `total_pages`/`total_books`는 이
    `will_process`가 참인 책들만 합산한다 — dry-run이나 skip 대상 page까지
    분모에 넣으면 실제로 진행되지 않는 page 때문에 bar가 끝까지 못 채워진다.
  - classify 자체가 실패(손상된 PDF 등)하면 예외를 삼켜 `_Classification.error`에
    담고, main loop에서 그대로 `status="failed"` 결과로 흘려보낸다(이전에는
    `_process_one`의 try/except가 classify 실패까지 함께 잡았는데, classify를
    분리한 뒤에도 개별 파일 실패가 배치 전체를 죽이지 않도록 이 처리를 유지했다).
- `TqdmBatchOcrProgress`가 outer bar(batch 전체 page, `total=total_pages`)와
  책마다 새로 만드는 inner bar(`TqdmOcrLogger`, `position=1, leave=False`)를
  함께 관리한다. `_BatchBookLoggerAdapter`가 inner logger에 event를 그대로
  전달하면서, `completed_pages` 증가분만큼 outer bar도 같이 전진시킨다.
  실패한 책은 `note_book_done(page_count, processed_page_count)`에서
  `page_count - processed_page_count`만큼 outer bar를 강제로 채워서, 실패해도
  batch 전체 progress가 멈추지 않는다.
- `BatchOcrProgress`를 Protocol로 두고 `NullBatchOcrProgress`(표시 없음),
  `FlatBatchOcrProgress`(plain/json 모드에서 책마다 독립된 flat logger를
  그대로 씀), `TqdmBatchOcrProgress` 세 구현으로 나눴다. `--log-mode`가
  plain/json/none인 배치 실행은 기존 flat 이벤트 스트림 그대로 남겨서, 이
  로그를 grep/tail로 소비하던 워크플로를 깨지 않았다.
- `OcrOverlayBatchRunner.__init__`의 `ocr_logger_factory: Callable[[Path],
  OcrLogger]` 파라미터를 `log_mode: OcrLogMode`/`enable_log_file: bool`로
  바꿨다. CLI 밖에서 직접 factory를 주입하는 외부 사용처가 없어서(테스트도
  기본값만 씀) 하위 호환 없이 바로 교체했다.

## 작동 방식

1. `ocr-overlay` CLI: `build_ocr_logger(mode, output_dir, enable_file=...,
   desc=f"OCR overlay: {pdf.name}")`로 logger를 만들고, `OcrOverlayBuilder.run()`이
   내부에서 `_emit()`으로 event를 밀어 넣는다. `TqdmOcrLogger`는 그 중
   `page_done`만 골라 bar를 전진시킨다.
2. `ocr-overlay-batch` CLI: `OcrOverlayBatchRunner.run()`이
   (a) 모든 PDF를 `_classify()`로 한 번씩 분류 → (b) `will_process`인 책들의
   page 합/책 수로 `build_batch_ocr_progress()` 호출 → (c) 각 classification을
   순회하며 target이 아니거나 dry-run/이미 존재하면 `progress.note_skip()`만
   부르고 즉시 결과를 반환, 실제 처리 대상이면 `progress.logger_for_book(...)`로
   책 전용 logger를 받아 `OcrOverlayBuilder`에 넘기고 끝나면
   `progress.note_book_done(...)`을 부른다.
3. 파일 로그(`ocr_log.jsonl`/`ocr_progress.json`)는 표시(progress)와 분리했다.
   batch에서는 `display_logger`(progress가 만든 것)와
   `JsonFileOcrLogger(artifact_dir)`를 `CompositeOcrLogger`로 묶어서, 화면에
   무엇을 보여주든 파일 기록은 `enable_log_file` 하나로만 켜고 끈다.

## 검증

- `uv run pytest` 84개 전체 통과. 신규 테스트: `TqdmOcrLogger`가
  `page_done`에만 전진하는지, `TqdmBatchOcrProgress`가 여러 책에 걸쳐 outer
  bar를 누적하는지, 실패한 책의 shortfall을 outer bar에 반영해 batch가 멈추지
  않는지, `build_batch_ocr_progress`가 mode별로 올바른 구현체를 고르는지.
  tqdm bar를 실제로 렌더링하지 않고 검증하기 위해 `TqdmOcrLogger`/
  `TqdmBatchOcrProgress`에 `file: TextIO | None` 파라미터를 추가해 테스트에서
  `io.StringIO()`로 리다이렉트했다(`disable=True`는 `.n`을 아예 갱신하지 않아
  검증에 못 쓴다는 걸 확인하고 이 방식을 택했다).
- `uv run ruff check` / `uv run ruff format --check` 통과(이 커밋이 건드린
  파일 기준; 기존 실험 파일들의 미포맷 상태는 그대로 뒀다).
- 실제 CLI로 수동 스모크 테스트: 캐시된 수리통계학 책 5쪽/3쪽을
  `--cache-policy only`로 돌려 tqdm bar가 한 줄로 0/5 → 5/5까지 올라가고
  `hit=`/`miss=` postfix가 표시되는지, PDF 파일명이 description에 나오는지
  확인했다. 빈 디렉터리로 `ocr-overlay-batch`도 실행해 `total_books=0`일 때
  progress bar 없이 정상 종료되는지 확인했다.
- 실제 batch 실행에서 outer/inner 두 bar가 함께 렌더링되는 모습은(여러 권짜리
  실 데이터 배치를 새로 도는 게 API 비용이 들어서) 수동으로 보지 못했다.
  단위 테스트로 진행 계산 로직은 검증했지만, 터미널에서 두 bar가 겹치지 않고
  깔끔하게 보이는지는 실제 batch 실행에서 확인이 필요하다.

## 대안과 제외한 선택지

- **classify를 두 번(사전 집계용 + 처리용) 하기**: `_process_one()` 구조를
  안 건드리고 앞에서 한 번 더 스캔하는 방식도 가능했지만, `classify_scan`이
  page를 렌더링해 판정하는 만큼 파일마다 두 번 도는 비용이 아깝다고 판단해
  `_classify()`로 분리하고 결과를 재사용하는 쪽을 택했다.
- **skip/dry-run 책의 page도 outer bar total에 포함**: 그러면 skip이 순간적으로
  bar를 확 채웠다가 실제 OCR 진행에서 다시 느려지는 것처럼 보여 ETA가
  왜곡된다. `will_process`인 책만 분모에 넣는 쪽으로 정리했다.
- **`ocr_logger_factory` 콜백을 유지하고 batch progress를 그 위에 얹기**: 외부
  주입 지점을 남겨두는 방식도 고려했지만, 실제로 그 콜백을 쓰는 곳이 CLI뿐이라
  불필요한 간접 계층이었다. `log_mode`/`enable_log_file`로 직접 받는 게 더
  단순했다.
- **postfix마다 `refresh=True`**: 기본 동작이지만, page당 여러 번(6~7회)
  postfix를 갱신하므로 매번 강제 redraw하면 오히려 다시 verbose해질 위험이
  있어 `refresh=False`로 뒀다(다음 `update()`가 어차피 다시 그린다).

## 남은 리스크

- 실제 여러 권짜리 batch 실행에서 outer+inner 두 bar가 터미널에서 겹치지
  않고 깔끔하게 갱신되는지는 API 비용 때문에 수동 확인을 못 했다(단위
  테스트로는 진행 계산만 검증). 다음 실제 batch 실행 때 육안으로 확인이
  필요하다.
- `classify_scan`을 처리 전에 미리 한 번 다 돌리므로, 파일이 아주 많은
  디렉터리(수백~수천 권)에서는 실제 OCR 시작 전 pre-classify 단계가 눈에
  보이는 지연으로 느껴질 수 있다(이전에도 각 파일 처리 직전에 classify를
  했으니 총 classify 비용 자체는 그대로지만, 이제는 그 비용이 앞으로 몰린다).
- `--log-mode plain`/`json`으로 batch를 돌리면 여전히 책마다 flat event
  스트림이 그대로 나온다(요청받은 tqdm 개선은 `tqdm` 모드에만 적용했다).
