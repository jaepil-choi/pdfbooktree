## 변경 배경

- bookmark-guided TOC page detection 결과를 단순 탐지 결과로만 남기면 후속 feature 분석이나 classifier 학습에 바로 쓰기 어렵다.
- 이번 작업의 목표는 bookmark가 있는 PDF에서 찾아낸 TOC page를 정답 positive로 삼고, 같은 PDF 안의 non-TOC page를 동일한 개수만큼 negative로 뽑아 page 단위 dataset을 만드는 것이다.
- 외부 Google Drive 경로처럼 PDF 수가 많은 디렉터리에서는 순차 실행이 느릴 수 있으므로, 파일 단위 병렬 worker를 CLI에서 조절할 수 있어야 했다.
- 기존 diagnostic은 bookmark가 없는 파일까지 모두 출력해 로그가 지나치게 verbose했다. 사용자가 실제로 보고 싶은 것은 bookmark가 있는 PDF와 dataset 생성 완료 상태이므로 기본 로그를 줄일 필요가 있었다.

## 결정 내용

- `TocPageDatasetRow` 모델을 추가했다. 한 row는 하나의 PDF page이며, `label=1`은 bookmark-guided detector가 찾은 TOC page, `label=0`은 같은 PDF에서 샘플링한 non-TOC page다.
- `BookmarkedPdfTocBatchResult`에는 `workers`, `dataset_row_count`, `dataset_rows`를 추가했다. 단일 PDF 결과인 `BookmarkedPdfTocDetection`에도 파일별 dataset row를 담는다.
- CLI에는 `--dataset-json`, `--dataset-csv`, `--random-seed`, `--workers`를 추가했다.
- negative sampling은 `random_seed` 기반으로 재현 가능하게 만들고, 각 PDF마다 positive page 수와 1:1이 되도록 non-TOC page를 뽑는다.
- 병렬화는 `ProcessPoolExecutor`를 사용했다. PyMuPDF document 객체는 process 간 공유하지 않고, worker 함수에는 경로와 설정값만 넘겨 각 process에서 PDF를 새로 연다.
- diagnostic은 기본적으로 `PDF 검색`, `bookmark 있음`, `TOC/dataset 생성 완료`, 최종 bookmark 보유 PDF 요약 중심으로 줄였다. bookmark가 없는 파일별 로그는 출력하지 않는다.
- CSV 저장은 `write_toc_page_dataset_csv`로 분리했다. list feature인 `line_final_numbers`는 CSV cell 안에 JSON 문자열로 저장한다.

## 작동 방식

- `BookmarkTocBatchDetector.run()`은 PDF 경로 목록을 찾은 뒤 `workers` 값에 따라 순차 처리 또는 `ProcessPoolExecutor` 처리를 선택한다.
- worker 함수 `_process_pdf_for_bookmark_toc`는 단일 PDF에 대해 bookmark 추출, text 추출, page feature 계산, bookmark-guided TOC detection, dataset row 생성을 한 번에 수행한다.
- bookmark가 없는 PDF는 `("skipped", None)`으로 반환하고 결과 row에 포함하지 않는다. batch summary의 `skipped_no_bookmark_count`에만 반영된다.
- TOC page가 탐지되면 탐지 page를 positive row로 만들고, `1..total_pages` 중 positive page를 제외한 후보에서 같은 수만큼 negative page를 샘플링한다.
- negative page는 앞부분 text search 범위 밖에 있을 수 있으므로 `extract_selected_page_texts`를 추가해 임의의 1-based PDF page text를 추출한다.
- positive page feature는 기존 `max_text_pages` 범위에서 계산한 feature를 우선 재사용하고, 누락된 positive page가 있으면 선택 page 추출로 보완한다.
- CLI에서 `--output-json`은 전체 batch 결과를 저장하고, `--dataset-json`과 `--dataset-csv`는 dataset row만 저장한다. 터미널 출력은 결과 요약만 보여준다.

## 대안과 제외한 선택지

- thread 기반 병렬화는 제외했다. PDF parsing과 feature 계산은 CPU 작업과 PyMuPDF 호출이 섞이므로, 파일 단위 process 병렬화가 더 명확하다.
- worker에서 직접 터미널에 출력하는 방식은 제외했다. 병렬 출력이 섞이지 않게 main process가 worker 완료 결과를 받아 diagnostic을 출력한다.
- bookmark가 없는 PDF에 runtime detector를 돌려 negative만 만드는 방식은 제외했다. 이번 dataset의 label source는 bookmark-guided TOC detection으로 한정한다.
- negative page를 앞부분 `max_text_pages` 안에서만 뽑는 방식은 제외했다. TOC page와 비교할 non-TOC page가 앞부분에 치우칠 수 있으므로 전체 PDF page 범위에서 샘플링한다.
- 전체 batch 결과를 항상 터미널에 크게 출력하는 방식은 제외했다. 대량 실행에서는 JSON/CSV 파일이 주 산출물이고, 터미널에는 요약만 충분하다.

## 남은 리스크

- `ProcessPoolExecutor`는 Windows에서 process 생성 비용이 있으므로 PDF 수가 아주 적을 때는 `workers=1`이 더 빠를 수 있다.
- Google Drive 동기화 폴더에서는 worker 수를 너무 높이면 CPU보다 디스크와 동기화 I/O가 병목이 될 수 있다. 현재 CLI는 사용자가 `--workers 8`처럼 직접 선택하게 한다.
- negative sampling은 현재 PDF 전체에서 균등 샘플링한다. 이후 학습 목적에 따라 앞부분 hard negative, body page negative, near-TOC negative 같은 전략을 추가할 수 있다.
- positive label은 bookmark-guided detector의 결과이므로 완전한 수작업 정답은 아니다. confidence와 source metadata를 함께 저장하지만, downstream 평가에서는 pseudo-label임을 고려해야 한다.
- dataset row가 batch 결과 JSON에도 포함되므로 대량 PDF에서는 `--output-json` 파일이 커질 수 있다. 필요하면 요약 전용 JSON 옵션을 후속으로 둘 수 있다.
