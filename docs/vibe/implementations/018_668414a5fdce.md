## 변경 배경

- 기존 runtime skip 정책은 bookmark가 있어도 `is_clean_bookmark_set`을 통과한 PDF만 제외했다.
- 프로젝트 방향은 bookmark가 있는 PDF를 runtime 처리 대상이 아니라 training/evaluation data preparation의 weak reference로 쓰는 것이다.
- 따라서 bookmark 기반 pseudo answer label 생성 흐름과 실제 `Processor` / `BatchProcessor` runtime 입력 필터를 명확히 분리할 필요가 있었다.

## 결정 내용

- `build_skip_reason`은 bookmark 품질과 무관하게 bookmark가 하나라도 있으면 skip 사유를 반환하도록 변경했다.
- `is_clean_bookmark_set`은 runtime skip 기준에서 제외하고, 학습/평가용 weak reference 품질 판단 helper로 의미를 좁혔다.
- CLI help 문구도 `기존 bookmark가 있으면 runtime 처리를 건너뛴다`로 수정했다.
- PRD에는 bookmark 기반 pseudo answer label은 training/evaluation data preparation에만 사용하고, runtime detector 입력에서는 bookmarked PDF를 제외한다는 정책을 명시했다.
- runtime detector 이후 LLM fallback 흐름은 3단계 구조로 문서화했다.

## 작동 방식

- `Processor.run`은 먼저 `extract_existing_bookmarks`로 PDF outline을 읽는다.
- `skip_existing_bookmarks=True`이면 `build_skip_reason(bookmarks)`를 호출한다.
- bookmark 목록이 비어 있지 않으면 `ProcessingResult(status="skipped")`를 반환하고 TOC detection, parsing, PDF 본문 처리로 진행하지 않는다.
- bookmark가 없는 PDF만 기존 TOC detection 경로로 내려간다.
- `detect-bookmark-toc`처럼 pseudo label 생성을 위한 별도 흐름은 bookmark가 있는 PDF를 계속 입력으로 사용할 수 있다.

## 대안과 제외한 선택지

- 기존처럼 clean bookmark만 skip하는 방식은 제외했다. runtime에서 bookmarked PDF를 처리하면 pseudo-label 생성 대상과 실제 처리 대상이 섞여 평가가 흐려진다.
- `is_clean_bookmark_set`을 삭제하지는 않았다. bookmark 품질 판단은 weak reference 선별과 분석에서 여전히 필요하다.
- bookmarked PDF를 강제로 재처리하는 별도 override는 이번 범위에 넣지 않았다. 현재 CLI에는 `--no-skip-existing-bookmarks`가 이미 있지만, 기본 runtime 정책은 skip이다.

## 남은 리스크

- `skip_existing_bookmarks=False`로 강제 처리하는 경우에는 bookmarked PDF도 기존 detector 경로로 내려갈 수 있다. 이 옵션이 앞으로도 필요한지 별도 정책 결정이 필요하다.
- ML detector는 학습 코드와 dataset 학습 흐름이 존재하지만, `Processor` runtime에는 아직 모델 artifact 로딩 경로가 연결되어 있지 않다.
- PRD에는 3단계 LLM fallback 구조가 정리되었지만 실제 구현은 후속 작업으로 남아 있다.
