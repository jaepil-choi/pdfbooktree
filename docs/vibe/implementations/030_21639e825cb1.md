- 전체 책 OCR overlay는 수백 page의 렌더링, 외부 OCR 호출, cache 재사용, PDF 생성 단계를 거치므로 터미널 출력이 없으면 멈춘 것처럼 보인다.

## 결정 내용

- `progress.py` 대신 `pdfbooktree.ocr.logger`를 추가했다. OCR 진행률은 runtime logging의 한 표현으로 보고, event log와 progress snapshot을 같은 모델로 처리한다.
- `OcrLogEvent`를 중심으로 builder가 실행 단계별 event를 emit한다.
- logger 구현체는 `JsonFileOcrLogger`, `PlainTextOcrLogger`, `JsonStdoutOcrLogger`, `RichOcrLogger`, `CompositeOcrLogger`, `NullOcrLogger`로 나눴다.
- CLI에는 `--log-mode auto|rich|plain|json|none`과 `--no-log-file`을 추가했다.
- 파일 로그는 기본 활성화되어 `ocr_log.jsonl`과 `ocr_progress.json`을 output dir에 남긴다.
- Upstage engine은 호출 전 현재 작업 디렉터리부터 `.env`를 찾아 로드한다.

## 작동 방식

- `OcrOverlayBuilder`는 optional `logger`를 받는다. 주입하지 않으면 `NullOcrLogger`를 사용하므로 기존 public API는 유지된다.
- builder는 시작, bookmark 확인, page 렌더링, raw cache hit, OCR API 호출 시작/완료, insertable cache/build, page 완료, overlay PDF 생성, stats 저장, 완료/실패 이벤트를 발생시킨다.
- ETA는 완료된 page 수와 전체 elapsed time의 단순 평균으로 계산한다. cache hit와 OCR call 시간이 섞이므로 추정치는 참고용이다.
- `JsonFileOcrLogger`는 모든 event를 `ocr_log.jsonl`에 append하고 최신 상태를 `ocr_progress.json`에 덮어쓴다.
- `RichOcrLogger`는 rich progress bar에 현재 page, event, ETA, cache hit/miss를 표시한다.
- `PlainTextOcrLogger`는 non-interactive 환경에서도 한 줄 로그를 계속 출력한다.
- `--log-mode auto`는 stderr가 TTY면 rich, 아니면 plain을 선택한다.

## 대안과 제외한 선택지

- 별도 `progress.py`는 만들지 않았다. 사용자가 필요한 것은 단순 진행률보다 실패 위치와 cache/API 상태까지 포함한 실행 관찰성이므로 logger가 더 적절하다.
- 파일 로그를 기본 off로 두지 않았다. 긴 OCR 작업은 터미널이 닫히거나 멈춘 것처럼 보일 수 있으므로 persistent snapshot이 기본으로 필요하다.
- `verify=False` 방식의 SSL 우회는 쓰지 않았다. 기존처럼 OS trust store 기반 SSL context를 유지한다.

## 남은 리스크

- ETA는 cache hit와 live OCR call이 섞이면 흔들릴 수 있다. 나중에 OCR call 전용 평균과 cache hit 전용 평균을 분리하면 더 정확해진다.
- Rich progress는 일부 터미널에서 rendering이 깨질 수 있다. 이때 `--log-mode plain`이나 `--log-mode json`을 쓰면 된다.
- `ocr_log.jsonl`은 page 수가 매우 많은 책에서 커질 수 있지만, event 단위 JSONL이라 분석과 tailing에는 유리하다.
