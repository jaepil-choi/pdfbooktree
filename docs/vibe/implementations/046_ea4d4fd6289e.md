## 결정 내용

- 입력 config는 `schema_version = 1`을 가진 TOML로 정의하고 외부 section을 `[processing]`, `[typography]`, `[markdown]`으로 제한했다. 표준 라이브러리 `tomllib`을 사용해 새 runtime dependency를 추가하지 않았다.
- 설정 우선순위는 `package defaults < TOML < 명시적으로 입력한 기존 CLI option < --set`으로 고정했다. 기존 긴 option은 호환을 위해 유지하고, 모든 field는 반복 가능한 `--set dotted.key=value`로 접근할 수 있게 했다.
- frozen dataclass의 `__post_init__`에서 Python API와 CLI가 공유하는 범위·타입·field 간 제약을 검증한다. field metadata를 schema, 기본 TOML, `config explain`의 공통 근거로 사용한다.
- `RunManifest` schema version을 1로 정의하고 input identity, resolved config와 hash, package/git identity, 상태와 timestamp, 실제 생성된 artifact를 기록한다.
- 기본 `process`는 input/config hash와 timestamp를 포함하는 새 run directory를 만들며 기존 directory를 덮어쓰지 않는다. 기존 flat output 계약이 필요한 사용자는 명시적으로 `--flat-output`을 사용한다.
- OCR cache와 run manifest가 동일한 SHA-256 규칙을 사용하도록 hashing utility를 공통 모듈로 이동했다.

## 작동 방식

- `resolve_processing_config()`가 dataclass 기본값을 만든 뒤 TOML, 기존 CLI override, `--set`을 순서대로 병합하고 최종 `ProcessingConfig`를 생성한다. 알 수 없는 section/field, 잘못된 schema version과 타입은 `ConfigError`로 거부한다.
- `config defaults`, `schema`, `init`, `explain`, `validate`가 각각 기본값 조회, JSON Schema 조회, 주석 포함 TOML 생성, field 설명, 최종 resolved config 검증을 제공한다. 조회·검증 명령은 human 또는 JSON 형식을 지원한다.
- 기본 `process`는 PDF hash와 page count를 계산하고 immutable run directory를 만든다. `config.resolved.json`과 초기 `run_manifest.json`을 기록한 뒤 manifest 상태를 `running`으로 전환하고 기존 `Processor`를 실행한다.
- 처리 성공 시 실제 존재하는 PDF, Markdown, report와 plan 경로만 manifest에 기록하고 상태를 `succeeded`로 바꾼다. 예외가 발생하면 오류 정보와 종료 시각을 기록하고 상태를 `failed`로 바꾼 뒤 예외를 다시 전달한다.
- `--flat-output`에서는 run directory와 manifest를 만들지 않고 이전과 동일하게 사용자가 지정한 output directory를 `Processor`에 전달한다.

## 대안과 제외한 선택지

- 모든 config field를 개별 CLI option으로 추가하지 않았다. option 수와 이름이 더 늘어 `--help` 발견성이 악화되므로 공통 option만 유지하고 전체 surface는 TOML과 `--set`으로 제공했다.
- YAML은 주석 표현은 좋지만 암묵적 타입 변환과 추가 dependency가 필요해 선택하지 않았다. JSON은 주석을 지원하지 않아 사람이 반복 편집하는 입력 config에 사용하지 않았다.
- 동일 output directory의 고정 파일명을 계속 덮어쓰는 방식을 기본값으로 유지하지 않았다. 재현성과 비교 안전성을 기본으로 하고 이전 동작은 `--flat-output`으로 격리했다.
- 이 커밋에서 `Processor` 내부 algorithm을 analyze/infer/apply로 분리하지 않았다. 먼저 config와 run identity를 고정해야 다음 단계의 public API와 artifact가 안정된 실행 단위에 연결되기 때문이다.

## 남은 리스크

- `Processor.run()`은 아직 분석, 추론, 검증, PDF/Markdown 적용을 한 번에 수행한다. plan-only 실행과 analysis 재사용은 Phase 2에서 분리해야 한다.
- 동일 input/config도 timestamp가 다르면 새 run이 생성된다. cache hit, resume와 analysis cache key는 후속 sweep 단계에서 정의해야 한다.
- 공통 JSON result/error envelope, stdout/stderr 분리, documented exit code는 아직 모든 command에 적용되지 않았다.
- 기존 긴 process option은 Rich help의 기본 폭에서 일부 이름이 생략된다. advanced option 축소와 help 예제 정리는 후속 단계가 필요하다.
- `batch`는 아직 single process와 같은 TOML/override/run manifest 계약을 사용하지 않는다.
- run manifest는 versioned이지만 plan과 기존 중간 artifact 전체가 독립 schema version을 가진 것은 아니다.
