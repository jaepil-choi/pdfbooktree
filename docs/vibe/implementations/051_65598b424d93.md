## 결정 내용

- `cli_contract.py`에 schema version 1의 `CommandResultEnvelope`,
  `CommandErrorEnvelope`, `CommandError`를 추가하고 package root에서 public
  export했다. JSON success는 `schema_version/command/ok/result`, error는
  `schema_version/command/ok/error`의 서로 배타적인 shape를 사용한다.
- 세 명령에 `--format human|json`과 `--debug`를 추가했다. 기본 human은 기존 Rich
  결과를 유지해 호환성을 보존하고, JSON final result는 stdout 한 줄, JSON error는
  stderr 한 줄로 분리한다. 예상하지 못한 예외의 traceback은 `--debug`에서만 다시
  노출한다.
- exit code는 성공/기존 outline 재사용 0, runtime/internal error 1,
  config/plan/input error 2, 예외 없이 실행됐지만 `ProcessingResult.status=failed`인
  경우 3으로 고정했다. processing failure는 이미 만들어진 validation/artifact
  정보를 버리지 않고 error `details`에 command payload 전체를 직렬화한다.
- immutable run에서는 `run.complete()` 또는 `run.fail()`로 manifest를 먼저
  최종화한 뒤 envelope를 출력한다. `apply`의 plan source SHA-256 기록도 같은 try
  범위에 넣어 기록 실패가 조용히 성공으로 끝나지 않게 했다.
- `--flat-output`도 missing/corrupt PDF를 `invalid_input` exit 2로 분류하도록 입력
  검증을 추가했다. manifest mode의 `create_run_context()`와 같은 의미를 가지게
  하되, 기존 run 생성 계약 자체는 변경하지 않았다.

## 작동 방식

- 각 단계형 command는 먼저 출력 형식을 검증하고 config를 resolve한다. config,
  plan, PDF 입력 오류는 command별 code(`invalid_config`, `invalid_plan`,
  `invalid_input`)와 exit 2로 즉시 stderr에 출력한다.
- flat mode는 실제 pipeline 호출을 runtime guard로 감싼 뒤 `ProcessingResult`를 바로
  payload로 사용한다. immutable run mode는 run identity/config/manifest를 만든 뒤
  pipeline과 manifest 완료를 수행하고, `run_id/run_dir/manifest_path/config_hash/result`
  wrapper를 payload로 사용한다.
- 정상 또는 `skipped` 결과는 success envelope로 stdout에 출력한다. validation이
  invalid여서 status가 `failed`면 `ProcessingFailedError`와 payload detail을 가진
  error envelope를 stderr에 출력하고 exit 3으로 끝낸다.
- runtime 예외는 run이 있으면 failed manifest를 먼저 기록한다. 기본 모드는
  `runtime_error` envelope와 exit 1로 끝나고, debug 모드는 manifest 기록 후 원래
  예외를 다시 발생시킨다.

## 대안과 제외한 선택지

- 기존 `print_config_output()`과 inspect의 `--json`을 즉시 공통 envelope로 바꾸지
  않았다. config/inspect/OCR/batch까지 한 커밋에서 바꾸면 호환 표면과 테스트 범위가
  지나치게 커지므로 단계형 lifecycle 세 명령만 먼저 전환했다.
- human 출력까지 envelope 형태로 감싸지 않았다. 사람이 읽는 기본 출력의 기존
  사용성을 유지하고, strict versioned contract가 필요한 agent는 명시적으로
  `--format json`을 선택하게 했다.
- `ProcessingResult.status=failed`를 runtime exception과 같은 exit 1로 합치지
  않았다. pipeline이 실행되고 validation/report/artifact가 남은 경우와 실행 자체가
  중단된 경우를 agent가 구분해야 하기 때문이다.
- progress event/JSONL protocol은 포함하지 않았다. 세 명령은 현재 별도 progress를
  stdout에 쓰지 않아 final result 분리를 먼저 완료할 수 있었고, event renderer는
  OCR/batch까지 포함하는 후속 단위가 적합하다.

## 남은 리스크

- Typer가 command callback 진입 전에 처리하는 필수 인자 누락, 알 수 없는 option,
  option 타입 오류는 여전히 Typer 기본 error 형식과 exit 2를 사용한다. 모든 parser
  오류까지 JSON envelope로 바꾸려면 app-level Click/Typer 예외 경계가 필요하다.
- config 명령은 일부 `--format json`, inspect는 `--json`, OCR/classify는 별도 log
  mode, batch는 Rich 출력만 사용한다. Phase 3 공통 계약은 아직 부분 완료 상태다.
- stdout final result와 stderr error는 분리됐지만 pipeline event protocol과 JSONL
  progress renderer는 없다. 장시간 OCR/batch 작업의 machine-readable progress는
  후속 구현이 필요하다.
- report JSON의 `report_path=null`과 최종 Python result의 실제 report path 비대칭은
  이번 범위에서 변경하지 않았다.
