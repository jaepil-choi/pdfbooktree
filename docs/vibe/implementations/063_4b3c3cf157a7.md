## 결정 내용

- 기존 OCR page logger와 별도로 `OcrBatchPreparationProgress`를 두어 discovery와 classification lifecycle을 표현했다. OCR 대상 page 합계를 알아야 생성할 수 있는 기존 outer bar보다 먼저 준비 단계 logger를 만들 수 있게 했다.
- `tqdm`, `plain`, `json`, `none` mode가 같은 lifecycle을 공유하게 했다. JSON mode에는 versioned `discovery_started`, `discovery_completed`, `classification_started`, `classification_progress`, `classification_completed`, `mupdf_warnings_collected` event를 추가했다.
- OCR outer bar는 실제 처리 대상의 page와 book만 세도록 유지하고, 분류 제외·기존 output 항목은 `skipped` postfix에 섞지 않기로 했다. 제외 규모는 분류 완료 요약과 batch report가 담당한다.
- PyMuPDF의 `mupdf_display_warnings`, `reset_mupdf_warnings`, `mupdf_warnings`를 PDF 작업 단위로 감싸 raw stderr 표시를 잠시 끄고 진단을 수집한 뒤 원래 표시 상태를 복원한다. 경고가 있어도 결과가 만들어졌다면 성공을 유지하며 실제 예외만 `failed`로 기록한다.
- 파일 결과와 CSV/detail JSONL에 `mupdf_warnings`를, summary와 CLI result에 target·실행 page 집계 및 MuPDF 경고 집계를 추가했다. 설치형 `use-pdfbooktree` skill의 저장소 사본과 package 번들 사본도 같은 계약으로 갱신했다.

## 작동 방식

- runner가 입력 directory와 recursive 여부를 먼저 알리고 PDF 탐색을 수행한 뒤 발견 개수를 출력한다.
- 발견한 PDF를 하나씩 분류하면서 classification bar를 전진시키고 누적 target 권수, target page 수, 오류 수를 postfix 또는 JSON event에 반영한다.
- 모든 분류가 끝나면 최소 page 조건 통과 수, scanned 수, OCR target 권수와 page 합계, 기존 output 수, 실제 실행 권수와 page 합계, 분류 실패와 MuPDF 경고 수를 한 줄로 요약한다.
- 분류와 OCR builder 호출 각각을 MuPDF 진단 capture 범위로 감싼다. 수집한 문자열은 해당 `OcrOverlayBatchFileResult`에 합쳐 CSV와 detail JSONL에 기록한다.
- 분류 후 실제 OCR 대상이 있으면 기존 이중 tqdm 구조로 전체 page와 현재 book page를 표시한다. 비대상 PDF를 순회할 때는 OCR bar를 변경하지 않는다.
- 처리 종료 후 `ocr_overlay_batch_summary.json`과 CLI result에는 `target_page_count`, `will_process_count`, `will_process_page_count`, `mupdf_warning_pdf_count`, `mupdf_warning_count`가 포함된다.

## 대안과 제외한 선택지

- 탐색·분류 중 단순 `print`를 직접 호출하는 방식은 JSON event 계약과 `none` mode를 깨뜨리고 tqdm 출력과 다시 충돌하므로 사용하지 않았다.
- MuPDF 진단을 전역적으로 영구 비활성화하는 방식은 원인 추적 근거를 잃고 single OCR 등 다른 workflow의 동작까지 바꾸므로 제외했다. 현재 PDF 작업 범위에서만 표시를 끄고 내용을 report에 보존한다.
- 모든 MuPDF 경고를 파일 실패로 승격하면 MuPDF가 정상 복구해 유효한 결과를 만든 문서까지 불필요하게 제외하므로 선택하지 않았다.
- 기존 bookmark low-quality 판정과 OCR target filter 의미를 바꾸는 것은 진행 관찰성과 진단 수집 문제와 별도 정책 변경이므로 이번 커밋에 포함하지 않았다.

## 남은 리스크

- PyMuPDF 경고 buffer와 표시 설정은 process global 상태다. 현재 OCR batch는 순차 처리하므로 안전하지만 향후 PDF 병렬 처리를 도입하면 capture 구간을 worker process별로 격리해야 한다.
- 복구 경고가 있어도 성공을 유지하므로 missing shading, 손상 font, ICC profile 문제로 일부 page의 시각 결과가 달라질 가능성은 남는다. 문제가 의심되는 파일은 detail JSONL의 경고와 산출 PDF를 함께 검토해야 한다.
- JSON mode는 분류 PDF마다 `classification_progress` event를 내보낸다. 대규모 directory에서는 event 수가 많아질 수 있으나 기계 소비자가 정확한 진행률을 계산할 수 있다는 점을 우선했다.
- 전체 300STUDY live OCR은 검증하지 않았으므로 장시간 실행 중 provider 오류, rate limit, 개별 PDF 렌더링 문제는 기존 파일별 실패·cache·재실행 경로로 대응해야 한다.
