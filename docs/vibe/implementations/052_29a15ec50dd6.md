## 결정 내용

- `config defaults`, `schema`, `init`, `explain`, `validate`와 `inspect page-count`, `text`, `bookmarks`, `ocr`, `plan`이 공통 schema version 1 결과 envelope를 사용하도록 했다.
- 모든 대상 명령에 `--debug`를 제공하고, `config init`과 inspect 명령군에는 정규 `--format human|json` 인터페이스를 제공했다.
- inspect의 기존 `--json` 옵션은 호환성을 위해 JSON 형식을 강제하는 별칭으로 유지했다.
- 잘못된 설정과 입력은 종료 코드 2, 예상하지 못한 실행 오류는 종료 코드 1로 분류했다.
- human 형식에서 문자열은 Typer로, 구조화된 값은 Rich로 출력해 기존 가독성을 유지했다.

## 작동 방식

- 각 명령은 `parse_output_format()`으로 출력 형식을 정규화한 뒤 성공 값을 `emit_command_result()`에 전달한다.
- JSON 형식은 stdout에 한 줄짜리 `CommandResultEnvelope`를 출력하고, 입력·설정 오류는 stderr에 `CommandErrorEnvelope`를 출력한다.
- `--debug`가 없으면 공통 오류 계약으로 변환하며, `--debug`가 있으면 원래 예외를 다시 발생시켜 traceback을 확인할 수 있게 한다.
- inspect의 `--json`이 지정되면 `--format` 값과 관계없이 JSON 결과 계약을 선택한다.

## 대안과 제외한 선택지

- 모든 명령의 기존 기본 형식을 JSON으로 일괄 변경하지 않았다. 사람이 사용하던 출력과 스크립트 호환성을 보존하고 정규 옵션으로 명시적인 전환을 제공하는 편이 안전하다고 판단했다.
- OCR·분류·배치의 진행 이벤트는 stdout/stderr 스트림 정책과 이벤트 스키마를 함께 설계해야 하므로 Phase 3C로 분리했다.

## 남은 리스크

- Typer가 명령 함수 호출 전에 처리하는 옵션 파싱 오류는 아직 공통 오류 envelope로 변환되지 않는다.
- OCR과 분류의 JSON 진행 로그가 stdout을 사용할 수 있어 최종 JSON 결과와 섞일 수 있다. 후속 이벤트 계약에서 진행 로그를 stderr로 분리해야 한다.
