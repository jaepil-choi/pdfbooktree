## 변경 배경

- PRD §3.5/§7.8~7.11/§15는 "heuristic-first, LLM-backup" 원칙과, runtime detector
  결과를 LLM이 검증/복구하는 3단계 fallback(start accept → backtrack_start →
  sequential recovery)을 규정한다. 그러나 이 구조는 그동안 PRD 문서에만 있었고
  구현·실험된 적이 없었다.
- 결정적 detector(`detect_toc_pages`)는 sample에서 recall이 자주 부족했다(예: john_hull
  0.5, luenberger 0.857). 또 한국어/OCR 목차는 결정적 regex 파서(`parse_toc_items`)가
  item을 0개 뽑아 range가 비었다(구현 노트 021의 남은 리스크).
- experiment 016에서 PRD 3단계 fallback을 solar-pro3 텍스트 경로로 검증해 로컬 5권 중
  4권을 precision 1.0 recall 1.0으로 복구했고(특히 binomial이 실패한 luenberger 7-20을
  backtrack으로 완벽 복구), 이 검증된 흐름을 패키지로 옮겨 `Processor`에 연결한다.
- 사용자가 "LLM TOC extractor가 반드시 포함되어야 한다"고 명시해, range reviewer와 item
  extractor 두 LLM 단계를 함께 wire한다.

## 결정 내용

- LLM 3단계 range fallback을 신규 모듈 `toc/llm_range_review.py`의 `LlmTocRangeReviewer`로
  분리했다. experiment 016의 `PageProbe`/`find_anchor`/`grow_block` 로직을 그대로 옮기되,
  단일 review 호출 동안의 page text·캐시·trace는 `_ReviewState`로 묶었다.
- anchor 결정과 경계 확장을 분리했다. `find_anchor`는 PRD 1·2·3단계로 "TOC가 확실한"
  page 하나만 고르고, `grow_block`이 anchor에서 **양방향 contiguous 확장**으로 start/end를
  정한다. backward 확장이 brief contents(예: John Hull page 5)를 detailed contents와
  merge한다. is_toc_start는 단계 분기에만 쓰고 경계 확장에는 쓰지 않는다(2단계에서 LLM이
  detailed contents 첫 page를 start로 봐도 backward merge가 brief contents를 흡수하도록).
- LLM은 Upstage Solar chat(`solar-pro3`) 텍스트 경로만 쓴다. Information Extraction은
  과금이라 호출하지 않는다. 그래서 정책에 맞춰 `LlmTocExtractionConfig.text_model` 기본값을
  `solar-pro2` → `solar-pro3`로 바꿨다.
- 파라미터를 전부 `LlmRangeReviewConfig`로 노출했다(model, scan_pages, max_backtrack,
  max_sequential, max_end_expand, end_gap_tolerance=0, prompt_max_chars, system_prompt).
  `end_gap_tolerance=0`은 TOC page가 contiguous하다는 가정으로, front-matter 목록 page를
  과하게 흡수하지 않게 한다(experiment 016에서 page 17 over-extension 방지).
- `Processor`는 `use_llm=True`일 때만 LLM을 탄다. `_review_toc_range`가 `detect_toc_pages`
  직후 range를 보정하고, 보정 page가 있으면 그것으로 downstream을 돌린다. `parse_toc_items`가
  0개를 뽑고 `use_llm`이면 `_extract_items_with_llm`가 같은 toc_pages에서 LLM item을 채운다.
- 테스트·재현을 위해 reviewer/extractor를 `Processor` 생성자에 주입할 수 있게 했고(`LlmTocExtractor`의
  기존 DI 패턴과 동일), 주입이 없으면 `use_llm`일 때 config로 lazy 생성한다.
- range review 결과는 `INTERMEDIATE_FILENAMES`에 `toc_range_review` 키를 추가해 저장한다.
  offset 추정 전에 끝나므로, offset fast-fail이 나도 근거가 남도록 toc_page_candidates와
  함께 offset 호출 **이전에** 먼저 저장한다.

## 작동 방식

- 모든 page 번호는 1-based다. `review(pdf, detection, total_pages)`는 앞 `scan_pages`만 page
  text로 확보한 뒤, detector 시작 page를 probe해 단계를 정한다.
  - 1단계 stage1_accept: 시작 page가 `is_toc_page` AND `is_toc_start`이면 anchor=시작 page.
  - 2단계 stage2_backtrack: 시작 page가 `is_toc_page`지만 첫 page가 아니면 anchor=시작 page
    (backward merge가 앞 경계를 복구).
  - 3단계 stage3_sequential_recovery: 시작 page가 TOC가 아니거나 detector 후보가 없으면
    page 1부터 순차 검토해 첫 TOC page를 anchor로 잡는다. 못 찾으면 stage3_failed로 빈 range.
- `grow_block`은 anchor에서 backward/forward로 `is_toc_page`가 이어지는 동안 확장하고,
  `end_gap_tolerance`를 넘는 연속 non-TOC page에서 멈춘다. 같은 page는 캐시로 한 번만 LLM에 묻는다.
- `Processor.run` 흐름: detect_toc_pages → (use_llm) range review → toc_pages 확정 →
  parse_toc_items → (0개 AND use_llm) LLM item 추출 → estimate_page_offset → heading
  alignment → content range. offset이 clean하지 않으면 기존 정책대로 `OffsetEstimationError`를
  전파한다(LLM 단계는 offset 이전이라 그 전에 이미 실행·기록된다).
- `status`는 출력 writer가 아직 stub이라 여전히 `failed`다(구현 노트 021과 동일 제약).

## 대안과 제외한 선택지

- range fallback을 `Processor`에 인라인으로 넣는 안은 제외했다. 별도 모듈+config로 분리해야
  실험 016과 1:1 대응되고 단위 테스트로 격리 검증할 수 있다.
- `find_anchor`에서 start 경계를 바로 확정(2단계에서 page 단위 backtrack)하는 안 대신, anchor만
  고르고 `grow_block`이 경계를 정하게 했다. brief/detailed contents가 별도 segment라 LLM이
  detailed 첫 page를 `is_toc_start=true`로 보는 경우에도 backward merge로 brief를 흡수하려면
  is_toc_start와 무관한 contiguous 확장이 필요했다.
- LLM을 항상 호출하는 안 대신 `use_llm` 게이트로 막아 기본 runtime은 결정적 경로만 쓰게 했다
  (PRD의 heuristic-first 원칙). low_confidence_threshold 기반 선택 호출은 후속 과제로 남겼다.
- item 추출에 image 경로(information-extract)를 쓰는 안은 과금이라 제외하고 solar-pro3 텍스트만
  쓴다.

## 남은 리스크

- 출력 writer(`write_bookmarked_pdf`, `export_markdown_tree`)가 여전히 stub이라 status는
  항상 `failed`다. range/item/offset이 모두 성공해도 `processed`가 될 수 없다.
- LLM range review를 현재는 `use_llm`이면 항상 호출한다. PRD가 말한 low-confidence 한정 호출은
  `low_confidence_threshold`로 게이트하는 후속 작업이 필요하다(비용/지연 최적화).
- experiment 016에서 john_hull page 17(페이지 번호 없는 technical notes 목록) 경계는 LLM이
  TOC로 포함했다. front-matter 목록 경계는 여전히 미세 오차가 날 수 있다(사용자가 4/5 수용).
- LLM item 추출은 temperature 0이어도 OCR 텍스트 변동으로 item 수가 실행마다 약간 달라질 수
  있다(showcase에서 102→109). 결정성 보장은 후속 과제다.
- offset fast-fail PDF(예: algorithm_nine)는 range review가 성공해도 파이프라인이 중단된다.
  수동 offset 지정 경로는 아직 없다(구현 노트 021의 남은 리스크와 동일).
